Nuxt UI v5 is currently in alpha. Follow the progress in the [v5 tracking issue](https://github.com/nuxt/ui/issues/6918) and share feedback on the [v5 roadmap](https://github.com/nuxt/ui/discussions/6610).

This guide lists the breaking changes from v4 and is updated as the alpha progresses.

## Migrate your project

Update to the latest v5 alpha:

::code-group{sync="pm"}

```bash [pnpm]
pnpm add @nuxt/ui@next
```

```bash [yarn]
yarn add @nuxt/ui@next
```

```bash [npm]
npm install @nuxt/ui@next
```

```bash [bun]
bun add @nuxt/ui@next
```

::

## Changes from v4

The dependencies of the [`Editor`](/docs/components/editor), [`Carousel`](/docs/components/carousel) and [`Table`](/docs/components/table) components are no longer installed with Nuxt UI. They are optional peer dependencies, so projects that don't use these components no longer download them.

### Theme shape

Every component now declares its elements under `slots`, and classes in `variants` and `compoundVariants` are always given per slot.

Components made of a single element, such as [Container](/docs/components/container), [Kbd](/docs/components/kbd), [Skeleton](/docs/components/skeleton) or the prose `p`, `li` and `code`, used to be themed with a top-level `base` key. They now have one slot like any other component, which some of them rename to `root` (see [`root` slot](#root-slot) below):

```diff
 export default defineAppConfig({
   ui: {
     container: {
-      base: 'max-w-(--ui-container-lg)'
+      slots: {
+        root: 'max-w-(--ui-container-lg)'
+      }
     },
     prose: {
       p: {
-        base: 'leading-7'
+        slots: {
+          base: 'leading-7'
+        }
       }
     }
   }
 })
```

This applies to BlogPosts, ChatShimmer, Container, DashboardGroup, DashboardResizeHandle, DashboardSidebarCollapse, DashboardSidebarToggle, FieldGroup, Form, Kbd, Link, Main, PageBody, PageColumns, PageGrid, PageList, PricingPlans and Skeleton, and to the prose `a`, `accordion-item`, `badge`, `blockquote`, `card-group`, `code`, `em`, `field-group`, `hr`, `icon`, `kbd`, `li`, `ol`, `p`, `steps`, `strong`, `tabs-item`, `tbody`, `td`, `th`, `thead`, `tr` and `ul`. [Link](/docs/components/link) gains a `ui` prop along the way.

A class written as a plain string in `variants` or `compoundVariants` used to apply to the `base` slot. It now has to name its slot:

```diff
 export default defineAppConfig({
   ui: {
     button: {
       variants: {
         size: {
-          md: 'text-base'
+          md: {
+            base: 'text-base'
+          }
         }
       },
       compoundVariants: [{
         color: 'neutral',
         variant: 'outline',
-        class: 'ring-default hover:bg-soft-hover'
+        class: {
+          base: 'ring-default hover:bg-soft-hover'
+        }
       }]
     }
   }
 })
```

The slot to name is the one `base` stood for: `root` on the components listed under [`root` slot](#root-slot), `base` on the others, Button included. TypeScript reports both changes in `app.config.ts`. A `vite.config.ts` or a plain JavaScript config gets a warning in the console during development, and the classes are ignored.

::note
A find and replace can't apply these on its own: the top-level `base` only moves for the components listed above, since every other component already had it under `slots`, and a `class` string only has to be wrapped inside `compoundVariants`, not where `class` is a prop. Overrides built at runtime rather than written as literals have to be checked by hand. If you call `tv` yourself from `@nuxt/ui/utils/tv`, the same two rules apply to the themes you pass it, and it now always returns one function per slot. Classes go to those slot functions, `ui.base({ class })`, since the call that builds them only takes variants.
::

### Child sizes

Themes no longer carry the size of the avatars, chips, badges and kbds a component renders. The `*Size` slots (`leadingAvatarSize`, `itemLeadingAvatarSize`, `itemLeadingChipSize`, `itemTrailingKbdsSize`, `avatarSize`, `linkLeadingAvatarSize`, `linkLeadingChipSize`, `linkTrailingBadgeSize`, `trailingBadgeSize` and `kbdsSize`) held size values, not classes, so they are removed. Each component now picks the same sizes in code: from its own `size` where it did before, and the fixed ones it always used otherwise, like the `2xl` avatar of Alert and Toast or the `sm` kbds of Tooltip. Set it on the child instead:

```diff
-<UButton :avatar="{ src: '/avatar.png' }" :ui="{ leadingAvatarSize: 'xs' }" />
+<UButton :avatar="{ src: '/avatar.png', size: 'xs' }" />
```

Items take it the same way, through `item.avatar.size`, `item.chip.size` or a kbd's `size`. A `*Size` value set in `app.config.ts` has no app-wide replacement: a component passes the size it derives to its child as a prop, so `<UTheme :props="{ avatar: { size: 'xs' } }">` only sizes standalone avatars. Set `avatar.size` on each instance, or size the child with classes through its slot, like `:ui="{ leadingAvatar: 'size-4' }"`. A size you add to a component yourself, like an `xxs` Button, gets the child sizes of `md`, since there's no slot left to set them for it.

In a slot template, `ui.leadingAvatarSize()` and the other `*Size` slot functions are gone. Set the size of your own avatar or chip directly, `2xs` for an avatar and `md` for a chip at the default size.

::note
This can't be applied by a find and replace: the size moves from `ui` to a prop of the child, which differs per component and per item.
::

### `root` slot

Slot names now follow one rule. `base` is the element a component stands for: the box of a control, anything that can sit in a [FieldGroup](/docs/components/field-group) such as a Button, a Badge, the `<input>` of an Input or the trigger of a Select, and the HTML element of a prose component, the `<p>`, the `<h1>`, the `<pre>`. Some of them wrap it in a `root`, others render it alone. On every other component, the outermost element is `root`.

The layout containers that called it `base` have it renamed, in `app.config.ui`, in the `ui` prop and in `<UTheme :ui>`:

```diff
-<UContainer :ui="{ base: 'max-w-5xl' }" />
+<UContainer :ui="{ root: 'max-w-5xl' }" />
```

```diff
 export default defineAppConfig({
   ui: {
     pageGrid: {
       slots: {
-        base: 'gap-4'
+        root: 'gap-4'
       }
     }
   }
 })
```

This applies to BlogPosts, Container, DashboardGroup, DashboardResizeHandle, FieldGroup, Form, Main, PageBody, PageColumns, PageGrid, PageList and PricingPlans. On [EditorToolbar](/docs/components/editor-toolbar), the toolbar moves from `base` to `root` and the bubble or floating menu around it from `root` to `menu`.

Everything else keeps its `base` slot: Button, Link, Badge, Kbd, Skeleton, ChatShimmer, every input and select, the prose components, and the buttons built on Button (ChatPromptSubmit, ContentSearchButton, DashboardSearchButton, DashboardSidebarCollapse, DashboardSidebarToggle). Toaster keeps it too, where it is each toast.

::note
A find and replace can't apply this blindly: `base` has to be renamed on the components listed here and kept on the others, so every match has to be read with the component it belongs to. TypeScript reports a leftover `base` in `app.config.ts` and on the `ui` prop in templates. In a `ui` object built at runtime, or in a plain JavaScript config, it is silently ignored.
::

### `data-slot` attributes

Every `data-slot` now carries the name of its component. They used to be shared, so `[data-slot="root"]` or `[data-slot="title"]` matched every component on the page. The outermost element of a component is named after it, and every other element is `<component>-<slot>`, with the slot written as in the theme:

```diff
-<div data-slot="root">
-  <div data-slot="header">
-    <div data-slot="title">
+<div data-slot="card">
+  <div data-slot="card-header">
+    <div data-slot="card-title">
```

```diff
-[data-slot="root"] { … }
+[data-slot="card"] { … }

-<UTabs :ui="{ trigger: 'in-[[data-slot=list]]:font-bold' }" />
+<UTabs :ui="{ trigger: 'in-[[data-slot=tabs-list]]:font-bold' }" />
```

The component name is the one in the docs URL, `page-hero`, `navigation-menu`, `content-toc`. The outermost element is the `root` slot, or `base` on the components that have no `root`, such as Button and Select, so `[data-slot="base"]` on a button becomes `[data-slot="button"]`. Overlays have no root element: their teleported content is `modal-content`, `popover-content`, `tooltip-content`.

A slot that renders another component is named after the component that owns the slot, not the one it renders. The icon of a Button is `button-leadingIcon`, the container of a PageHero is `page-hero-container`. The rendered component's own name only shows where you use it directly: a standalone `<UIcon>` has none and a standalone `<UContainer>` is `container`. What sits inside it keeps its own names, so the icon inside the avatar of an Empty is `avatar-icon`.

Components that emitted no `data-slot` now have one on their root, among them Container, Form, FieldGroup, Kbd, Link, Main, Skeleton, the Page layout components and the buttons built on Button. Prose components still emit none.

To find what to update:

```bash
rg -n "data-slot=[\"']?[A-Za-z]|data-\[slot=" --glob '!node_modules'
```

::note
This can't be applied by a find and replace, and no codemod covers it: the selectors live in stylesheets, in class strings, in `querySelector` calls and in end-to-end tests, and the same old value maps to a different new one depending on the component it belongs to, `leadingIcon` being `button-leadingIcon` in one place and `input-leadingIcon` in another. Inspect the element in the browser to read its new value. A selector that is left behind stops matching without any error.
::

### Accent color

Component themes no longer repeat their classes for every color. The `color` prop sets a `--ui-accent` variable on the element, and the classes read it through new `accent` utilities such as `bg-accent`, `text-accent-foreground`, `bg-accent-soft` and `ring-accent-border`. [Accent](/docs/getting-started/theme/design-system#accent) lists the ones you can rely on.

Every color, `neutral` included, renders as before, with six exceptions, and the few [semantic tokens](#semantic-tokens) changes. A linked Banner hovers at 75% like Button instead of 90%. Callout text uses the color itself instead of its 600 and 300 shades. A Timeline paints its pending indicators itself, so an item's `avatar.color` no longer tints them. The items of a CheckboxGroup with `variant="table"` take a Checkbox's own `color` instead of the group's. A colored Calendar highlights and hovers its cells at 15% of the color instead of 20%, like every other soft hover. A checked item of the `card` and `table` variants of Checkbox, CheckboxGroup and RadioGroup has a border in the color itself instead of the color at 50%. For `neutral`, that border goes from `inverted` at 50% to the full `inverted` color, much darker in light mode and lighter in dark mode.

```diff
-<button class="… text-inverted bg-primary hover:bg-primary/75 …">
+<button class="… [--ui-accent:var(--ui-primary)] text-accent-foreground bg-accent hover:bg-accent-hover …">
```

`:ui` overrides and `compoundVariants` keyed on `color` keep working, since `bg-accent` merges with `bg-primary` or `bg-red-500` like any other background color. What changes is the class names components render:

- Stylesheets, `querySelector` calls or tests that look for `.bg-primary` or `.text-error` on a component need to look for the `accent` classes and the `[--ui-accent:…]` class instead.
- A replacer function drops the `[--ui-accent:…]` class along with the classes it replaces, so the component loses its color. That covers a function on `variants.color` in `app.config.ui`, and a function in `:ui` or `class` on the slot that carries the color, usually the root: `<UInput :ui="{ root: () => 'w-full' }" />` now renders without one. Keep the scope class in what the function returns.
- An app that declares its own `--color-accent` in `@theme` overrides the one Nuxt UI declares, and every component follows it. Rename yours.
- The classes each variant takes for a color moved from the theme's `compoundVariants` into its `variants`, except where a color changes more than the accent: DropdownMenu and ContextMenu items, whose color is optional per item, and Calendar, ChatMessage and the prose Callout, whose `neutral` is a design of its own. Your `app.config.ui` variants now come after them, so an override that used to lose silently applies, like `variants.variant.solid: { base: 'bg-red-500' }` on Button, which lost to `bg-primary`.

`neutral` is a color like the others. A new `--ui-neutral` variable, shade `900` of its palette in light mode and `50` in dark mode, goes through the same classes, and the neutral scope points the accent roles at the surface tokens such as `bg-soft`, `text-default` and `ring-strong`, so it keeps its current look. Callout, inline Code, Calendar and ChatMessage keep their own neutral classes.

Neutral text, rings and borders now follow `--ui-neutral` where they used `--ui-text-highlighted` or `--ui-border-inverted`, like the active link of Tabs or NavigationMenu and the focus ring of Input. In light mode the values are the same. In dark mode a solid neutral component, and those neutral accents, use shade `50` of the palette instead of pure white.

Setting `--ui-accent` through `class` also gives a component a color outside the `color` prop, without repeating its classes:

```vue
<UButton class="[--ui-accent:var(--color-indigo-500)]" variant="soft" />
<UInput highlight class="[--ui-accent:var(--color-indigo-500)]" />
```

::note
This can't be applied by a find and replace: selectors on color classes have to be read one by one, and the color name no longer appears in a component's classes, only in its `--ui-accent` class.
::

### Semantic tokens

The surface tokens are renamed after the accent roles, so a word means the same thing on both sides: `bg-soft` is always neutral, `bg-accent-soft` follows `color`. Their CSS variables take the property they style as a prefix, like `--ui-bg-soft` or `--ui-border-strong`.

```diff
-<div class="bg-default text-dimmed">
+<div class="bg-surface text-faint">
-<div class="bg-elevated hover:bg-accented">
+<div class="bg-soft hover:bg-soft-hover">
-<div class="hover:bg-elevated/50">
+<div class="hover:bg-tint">
-<p class="text-toned">
+<p class="text-default">
-<div class="ring ring-accented">
+<div class="ring ring-strong">
-<span class="ring-2 ring-bg">
+<span class="ring-2 ring-surface">
```

The same renames apply with any variant or modifier, `hover:bg-accented/75` becoming `hover:bg-soft-hover/75`, to `ring-*` and `divide-*`, and to the gradient stops of a background token, `from-default` becoming `from-surface`. `bg-elevated` with another opacity keeps it, `bg-elevated/75` becomes `bg-soft/75`. The utilities in the page's background color take the same word, `ring-bg`, `border-bg`, `fill-bg` and `stroke-bg` becoming `ring-surface`, `border-surface`, `fill-surface` and `stroke-surface`.

| v4 | v5 |
| --- | --- |
| `--ui-bg` | `--ui-bg-surface` |
| `--ui-bg-elevated` | `--ui-bg-soft` |
| `--ui-bg-accented` | `--ui-bg-soft-hover` |
| `--ui-text` | `--ui-text-default` |
| `--ui-text-dimmed` | `--ui-text-faint` |
| `--ui-text-toned` | Removed, `--ui-text-default` |
| `--ui-border` | `--ui-border-default` |
| `--ui-border-accented` | `--ui-border-strong` |

`--ui-bg-muted`, `--ui-bg-inverted`, `--ui-text-muted`, `--ui-text-highlighted`, `--ui-text-inverted`, `--ui-border-muted` and `--ui-border-inverted` keep their names. Two tokens are new. `--ui-bg-tint` is behind `bg-tint`, the fill of hovered and highlighted items, and `--ui-focus` behind `outline-focus`, the focus outline of components without a `color` prop. Both are unset by default: the utilities mix `--ui-bg-soft` at 50% and `--ui-primary` at 25% on the element, so a subtree that overrides those follows, and setting the token overrides the mix. `ring-offset-bg` becomes `ring-offset-surface`, and the unused `divide-bg` and `outline-default` utilities are removed.

The tokens, with `--ui-radius`, `--ui-container` and `--ui-header-height`, move from `@layer theme` to `@layer base` at zero specificity, like the palettes, so an override of yours in `@layer base` now wins over them. An override in `@layer theme` now loses: move it to `base` or out of any layer.

A few components look slightly different:

- The `tint` role of the colors goes from 10% to 5% of the color, half of `soft` like `bg-tint` for neutral. Colored items highlighted in DropdownMenu and ContextMenu, the `soft` and `subtle` Alert and a hovered prose Card are lighter.
- With `color="neutral"`, the components whose border comes from the `border` accent role use `--ui-border-muted`, the border meant for a fill. The `subtle` Button, Badge, Kbd and Alert are lighter in light mode than with `--ui-border-accented` and the same in dark mode. The `outline` Alert and ChatMessage, and the `subtle` ChatMessage, are the same in light mode and one shade lighter in dark mode than with `--ui-border`.
- The soft hover of `color="neutral"`, like a hovered `soft` Button, is `--ui-bg-soft-hover` itself instead of 75% of it.
- The FileUpload dropzone, hovered or with a file dragged over it, uses `bg-tint`, 50% of `--ui-bg-soft` instead of 25%.
- `text-toned` merges into `text-default`, one shade darker in light mode and lighter in dark mode, on BlogPost, ChangelogVersion, Empty, PageCard, PageCTA, PricingPlan, PricingTable, User and the prose Field.

::note
The class and variable renames can be applied by a find and replace on whole names, so that `--ui-text` doesn't catch `--ui-text-muted`, as long as `bg-elevated/50` is replaced before `bg-elevated`. An override of `--ui-text-toned` in your CSS has no token of its own left: move it to `--ui-text-default` if it should still apply. An override of an old variable that the find and replace misses is silently ignored. Classes built at runtime, like `` `bg-${tone}` ``, have to be checked by hand.
::

### `theme.colors` option

The `theme.colors` option is removed. Components accept a fixed set of colors, `primary`, `secondary`, `success`, `info`, `warning`, `error` and `neutral`, which you still map to any Tailwind palette, now in your CSS (see [`ui.colors` option](#uicolors-option)). Themes no longer need to know your aliases at build time. Trimming the list no longer saves any CSS either, since a color now costs one class.

```diff
 export default defineNuxtConfig({
   ui: {
-    theme: {
-      colors: ['primary', 'secondary', 'tertiary']
-    }
   }
 })
```

An extra alias like `tertiary` is declared in your CSS instead, and applied to a component through its `--ui-accent` variable, or through its `color` prop once you add it to that component's `color` variant in `app.config.ts`. [Extend colors](/docs/getting-started/theme/colors#extend-colors) shows both:

```diff
-<UButton color="tertiary" />
+<UButton class="[--ui-accent:var(--ui-tertiary)]" />
```

Its value moves to your CSS with the recipe. Nuxt UI no longer bridges its shades either, so declare `--color-tertiary-600` and the others in `@theme` if you use classes like `text-tertiary-600`.

::note
TypeScript reports the removed option in `nuxt.config.ts` or `vite.config.ts` and a `color` value outside the seven aliases. In plain JavaScript they are silently ignored, and a component given an unknown color takes the color of its closest colored ancestor, or none. Moving a custom alias from `color` to `class` can't be done by a find and replace when the component already has a `class`, binds `color` dynamically, or takes the color per item.
::

### `ui.colors` option

Colors move from `app.config.ts` to your CSS, where the `@nuxt/ui/colors` Tailwind plugin points each alias at a palette. Nuxt UI no longer generates a `<style>` from your app config at runtime, and no longer ships Tailwind's color table to the browser:

```diff [app.config.ts]
 export default defineAppConfig({
   ui: {
-    colors: {
-      primary: 'indigo',
-      neutral: 'zinc'
-    }
   }
 })
```

```diff [main.css]
 @import "tailwindcss";
 @import "@nuxt/ui";
+
+@plugin "@nuxt/ui/colors" {
+  primary: indigo;
+  neutral: zinc;
+}
```

With Vue, remove `colors` from the `ui` options of your `vite.config.ts` the same way. A custom palette keeps working by name, like `primary: brand` with `--color-brand-50` to `--color-brand-950` in `@theme`.

The plugin writes each alias as `--ui-color-primary-50` to `--ui-color-primary-950`. To change colors at runtime, like `updateAppConfig` did, set those variables in a `<style>` instead, as shown in [Change colors at runtime](/docs/getting-started/theme/colors#change-colors-at-runtime).

::note
The seven aliases of a static `colors` object move as is. An extra alias like `tertiary` becomes a `--ui-tertiary` variable instead, see [`theme.colors` option](#themecolors-option). Colors set at runtime with `updateAppConfig` or by writing to `appConfig.ui.colors` can't be moved by a find and replace, and reading `appConfig.ui.colors` now gives `undefined`. TypeScript only reports the removed key in `app.config.ts` when `colors` is the only key under `ui`. Next to other keys, and in a `vite.config.ts` or plain JavaScript, it is silently ignored and the aliases keep their default palettes, so remove it by hand.
::

### `theme.transitions` option

The `theme.transitions` option is removed. Components always carry their transition classes, such as `transition-colors` on hover and active states, and movement transitions already stop when the user asks for reduced motion.

```diff
 export default defineNuxtConfig({
   ui: {
-    theme: {
-      transitions: false
-    }
   }
 })
```

To keep transitions off across your app, turn them off in your CSS instead:

```css [main.css]
@layer base {
  *, ::before, ::after {
    transition: none !important;
  }
}
```

::note
TypeScript reports the removed option in `nuxt.config.ts`. In a `vite.config.ts` or a plain JavaScript config it is silently ignored, and transitions come back.
::

### `theme.defaultVariants` option

The `theme.defaultVariants` option is removed. The default `color` and `size` are resolved at runtime now, so move them to `ui.defaultVariants` in your `app.config.ts`. They still only replace the `primary` and `md` defaults.

```diff [nuxt.config.ts]
 export default defineNuxtConfig({
   ui: {
-    theme: {
-      defaultVariants: {
-        color: 'neutral',
-        size: 'sm'
-      }
-    }
   }
 })
```

```diff [app.config.ts]
 export default defineAppConfig({
   ui: {
+    defaultVariants: {
+      color: 'neutral',
+      size: 'sm'
+    }
   }
 })
```

With Vue, the value moves from `theme` to `ui` in the plugin options of your `vite.config.ts`:

```diff [vite.config.ts]
 ui({
-  theme: {
+  ui: {
     defaultVariants: {
       color: 'neutral',
       size: 'sm'
     }
   }
 })
```

To change them for part of your app only, use the `'*'` key of [`<UTheme :props>`](/docs/components/theme#default-variants): `<UTheme :props="{ '*': { size: 'sm' } }">`.

The themes in `#build/ui/*` no longer carry these defaults either: a theme you import from there keeps the library's `defaultVariants`.

::note
The value moves from `nuxt.config.ts` to `app.config.ts`, which a find and replace within one file can't do. TypeScript reports the removed option in `nuxt.config.ts`. In a `vite.config.ts` or a plain JavaScript config it is silently ignored, and components go back to `primary` and `md`.
::

### `theme.unstyled` option

The `theme.unstyled` option is removed. Components are unstyled at runtime now, per subtree with [`<UTheme unstyled>`](/docs/components/theme#unstyled) or app-wide with `ui.unstyled` in your `app.config.ts`:

```diff [nuxt.config.ts]
 export default defineNuxtConfig({
   ui: {
-    theme: {
-      unstyled: true
-    }
   }
 })
```

```diff [app.config.ts]
 export default defineAppConfig({
   ui: {
+    unstyled: true
   }
 })
```

With Vue, the value moves from `theme` to `ui` in the plugin options of your `vite.config.ts`, like `defaultVariants`.

Components render the same markup as before: only the classes you supply through `class`, `ui` or `app.config.ui` remain, plus the `[--ui-accent:…]` class of the `color` prop, which styles nothing on its own. The theme classes are still generated in your CSS, since Tailwind still scans the themes, but no component uses them. v4 left them out by blanking the themes at build time, so an unstyled app now ships more CSS. A theme you import from `#build/ui/*` keeps its classes too.

::note
The value moves from `nuxt.config.ts` to `app.config.ts`, which a find and replace within one file can't do. TypeScript reports the removed option in `nuxt.config.ts`. In a `vite.config.ts` or a plain JavaScript config it is silently ignored, and components get their styles back.
::

### `theme.prefix` option

The `theme.prefix` option moves to `tailwindPrefix`. It was the last option under `theme`, which is removed:

```diff [nuxt.config.ts]
 export default defineNuxtConfig({
   ui: {
-    theme: {
-      prefix: 'tw'
-    }
+    tailwindPrefix: 'tw'
   }
 })
```

With Nuxt, you can also remove it when a stylesheet in your `css` option imports Tailwind CSS with the prefix, as Nuxt UI reads it from there. With Vue, it moves the same way in the plugin options of your `vite.config.ts`, and has to stay there: the Vue plugin doesn't read it from your CSS.

::note
TypeScript reports the old option in `nuxt.config.ts` and `vite.config.ts`. In a plain JavaScript config it is silently ignored: with Nuxt the prefix is still read from the stylesheet in your `css` option that imports Tailwind CSS, with Vue components render their classes without it.
::

Components also prefix their classes at runtime now. The themes in `#build/ui` keep their classes unprefixed, and `#build/ui.css` gives Tailwind the prefixed classes through `@source inline(...)`. Components render the same classes as before.

If you import a theme from `#build/ui/*` and read its classes yourself, they no longer carry the prefix. Resolve it with `tv` from `@nuxt/ui/utils/tv` and the overrides `useComponentOverrides` builds, as shown in [Variants engine](#variants-engine). These carry the prefix, and `tv` leaves the classes that already have it as they are.

### `experimental.componentDetection` option

Component detection is on by default and leaves `experimental`, which is removed. Nuxt UI only generates the CSS of the components your app uses, so an app that didn't set the option ships less CSS, about 9 kB gzip less for an app that uses some 25 components:

```diff [nuxt.config.ts]
 export default defineNuxtConfig({
   ui: {
-    experimental: {
-      componentDetection: ['Modal']
-    }
+    componentDetection: ['Modal']
   }
 })
```

With Vue, it moves the same way in the plugin options of your `vite.config.ts`. Set `componentDetection: false` to keep the CSS of every component.

TypeScript reports `experimental` in `nuxt.config.ts` and `vite.config.ts`. In a plain JavaScript config it is silently ignored: detection stays on, but the components you listed are no longer added, so move the list.

::note
This can't be applied by a find and replace for apps that didn't set the option. Detection can miss a component resolved from a name built at runtime, like `<component :is="'U' + name" />`, or used only in remote content: list those in `componentDetection`. In development, such a component logs a warning in the browser console when it renders. Markdown in each layer's `content/` directory is scanned for `::u-button` and `:u-button`, and what prose components render is always included.
::

### Stylesheet paths

The stylesheets move to `dist/runtime/css/`. `@import "@nuxt/ui"` resolves as before, a path into the package doesn't:

```diff
-@import "@nuxt/ui/runtime/index.css";
+@import "@nuxt/ui";
```

`#build/ui.css` now holds only the sources Tailwind scans, not the styles, so import `@nuxt/ui` instead of it too. To put Nuxt UI in a cascade layer, import `@nuxt/ui/sources` at the top level and `@nuxt/ui/base` in the layer.

### Variants engine

Nuxt UI no longer depends on [Tailwind Variants](https://www.tailwind-variants.org/). Components are styled by an engine that ships with the library. `slots`, `variants`, `compoundVariants` and `defaultVariants` behave as before, and every theme in Nuxt UI resolves to the same classes.

Your `:ui` overrides keep working untouched. `app.config.ui` keeps its shape apart from the two changes described in [Theme shape](#theme-shape), but the order its classes apply in changes, see below. What follows only matters if you use `tailwind-variants` directly, or rely on one of the edge cases listed at the end.

If you import `tailwind-variants` in your own code, it is no longer installed for you:

::code-group{sync="pm"}

```bash [pnpm]
pnpm add tailwind-variants
```

```bash [yarn]
yarn add tailwind-variants
```

```bash [npm]
npm install tailwind-variants
```

```bash [bun]
bun add tailwind-variants
```

::

If you import its types, `@nuxt/ui` exports its own for the surface the engine supports: `ClassValue`, `ClassProp`, `TVTheme`, `TVOverrides`, `TVVariants`, `TVCompoundVariants`, `TVDefaultVariants`, `TVProps`, `TVReturnType`, `TVSlots` and `VariantProps`:

```diff
-import type { ClassValue, VariantProps } from 'tailwind-variants'
+import type { ClassValue, VariantProps } from '@nuxt/ui'
```

The config type is renamed, since `TVConfig` already means something else in Nuxt UI (the shape of `app.config.ui`):

```diff
-import type { TVConfig } from 'tailwind-variants'
+import type { TVMergeConfig } from '@nuxt/ui'
```

The generics take one type argument, the theme: `TVVariants<T>`, `TVCompoundVariants<T>`, `TVDefaultVariants<T>`, `TVProps<T>` and `TVReturnType<T>`, with `TVTheme` for what a theme may contain and `TVOverrides<T>` for what `app.config.ui` may add to one. Types with no equivalent, such as `TVCompoundSlots` or `TVLite`, describe features the engine doesn't have.

The engine's own `tv` takes the theme and the overrides as two arguments, and what it returns is only callable, it no longer carries the theme it was built from:

```diff
-const ui = tv({ extend: theme, ...appConfig.ui?.button })(props)
+const ui = tv(theme, appConfig.ui?.button)(props)
```

Called with plain overrides, `tv` merges with the default config and applies no prefix: it no longer reads `app.config.ui.tv` or `tailwindPrefix` itself. To resolve classes the way Nuxt UI's components do, with those two and `<UTheme unstyled>`, pass it the overrides `useComponentOverrides` builds:

```diff
+import { useComponentOverrides } from '@nuxt/ui/composables'
+
-const appConfig = useAppConfig()
-const ui = computed(() => tv(theme, appConfig.ui?.myComponent)(props))
+const overrides = useComponentOverrides(ui => ui.myComponent)
+const ui = computed(() => tv(theme, overrides.value)(props))
```

`useComponentOverrides` reads your component's entry from `app.config.ui`, then from the `ui` and `variants` of each `<UTheme>` around it.

::note
None of these changes can be applied by a find and replace: `TVConfig` is a valid Nuxt UI type too, so only imports coming from `tailwind-variants` should change, the type argument lists have to be read one by one, and a `tv` call has to be split where `extend` sits in its object.
::

Slot classes set in `app.config.ui` now win over the theme's `variants` and `compoundVariants`, the way the `ui` prop always has. They used to be merged beneath them, so a class like `text-inherit` on a slot silently lost to a theme variant setting `text-muted`, and the only way around it was to repeat the theme's variant combination in your own `compoundVariants`:

```diff
 export default defineAppConfig({
   ui: {
     avatar: {
       slots: {
         fallback: 'text-inherit'
-      },
-      compoundVariants: [{
-        color: 'neutral',
-        class: { fallback: 'text-inherit' }
-      }]
+      }
     }
   }
 })
```

The order is now the whole theme first, its slot classes, `variants` and `compoundVariants`, then yours in the same order, then the `ui` and `class` props. So anything you set wins over the theme, whatever form the theme rule takes.

That includes the theme's compounds that make room for something: the icon padding of Input, Select and the other fields (`leading` and `trailing` for each `size`), the button padding of InputNumber (`increment`, `decrement`), and `square` on Button and Badge. A padding you set now wins over them, so a leading icon overlaps the text and a square button loses its shape. Repeat the exception in your override for the sizes you change:

```diff
 export default defineAppConfig({
   ui: {
     input: {
       variants: {
         size: {
           md: { base: 'px-3' }
         }
-      }
+      },
+      compoundVariants: [{
+        size: 'md',
+        leading: true,
+        class: { base: 'ps-9' }
+      }]
     }
   }
 })
```

A slot class that conflicts with one of the theme's variants or compounds now wins over it. A ring color on every checkbox, `checkbox.slots.base: 'ring ring-black/8'`, hides the red ring a checkbox shows in a form error through `highlight`. Scope it to the case instead:

```diff
 export default defineAppConfig({
   ui: {
     checkbox: {
       slots: {
-        base: 'ring ring-black/8'
+        base: 'ring'
-      }
+      },
+      variants: {
+        highlight: {
+          false: { base: 'ring-black/8' }
+        }
+      }
     }
   }
 })
```

Overriding one variant no longer changes the order the theme's own variants apply in, which used to let an unrelated theme variant win on another slot. Function slots still replace the slot's default classes with the variants applied on top, and are now called once per configuration instead of on every render, see [function slots](/docs/getting-started/theme/components#function-slots).

The `activeClass` and `inactiveClass` props of [Link](/docs/components/link) and [Button](/docs/components/button) follow the same rule. They were folded into the `active` variant, so a class like `hover:text-primary` lost to the theme's own `hover:text-default`. They are now merged last, after the `class` prop.

::note
This can't be applied by a find and replace. A slot class that was losing to the theme starts to apply, so look at the components you override in `app.config.ui` for classes that conflict with one of their variants, and drop the `compoundVariants` you only wrote to force a slot class through.
::

The `app.config.ui.tv` keys are named after `tailwind-merge`, which is an implementation detail of the engine rather than something you configure. They drop the prefix:

```diff
 export default defineAppConfig({
   ui: {
     tv: {
-      twMerge: false,
-      twMergeConfig: { prefix: 'tw' }
+      merge: false,
+      mergeConfig: { prefix: 'tw' }
     }
   }
 })
```

The themes also move off the deprecated `bg-gradient-to-*` utilities, which Tailwind renamed to `bg-linear-*` in v4. Same CSS, so this only matters if your own stylesheet targets those class names on Marquee or PageAside.

The engine leaves out three things `tailwind-variants` accepted, none of which any Nuxt UI theme uses:

- `compoundSlots`. A theme that declares it loses those classes silently, since nothing reads the key. Move each entry to a per-slot `class` object in `compoundVariants`, or to the slots themselves when it had no condition.
- The second `config` argument of `tv()`. `app.config.ui.tv` is the one place to configure merging.
- The `className` alias of `class`, a React convention with no meaning in Vue. A `compoundVariants` entry in `app.config.ui` that used it should say `class`.

One edge case resolves differently:

- A `(defaults) => classes` replacer on a slot with no classes now receives `''`, where it used to receive `undefined` and could emit the class `undefined`. Under `<UTheme unstyled>` this means the replacer runs where it used to be skipped.

### Theme slot classes

The `ui` of a `<UTheme>` now merges with the `ui` of the components inside it, and with the `ui` of the Themes around it, instead of being replaced by them on the same slot. The nearest still wins a conflict, and the other classes still apply, so you no longer repeat the Theme's classes to keep them:

```diff
 <UTheme :ui="{ button: { base: 'rounded-full shadow-lg' } }">
-  <UButton :ui="{ base: 'rounded-none shadow-lg' }" />
+  <UButton :ui="{ base: 'rounded-none' }" />
 </UTheme>
```

A Theme's slot classes and `variants` apply at the same point as your app config's, after the whole theme, compound variants included, and the nearest Theme wins.

To drop a Theme's classes on one component, give the component's own `ui` a function, which replaces everything the slot resolved.

A function in a Theme's `ui` works like one in `app.config.ui` now: it replaces the component theme's classes for that slot when the component is built, and the variants, compound variants and the plain classes of `app.config.ui` and other Themes still apply on top, even from a farther level. It no longer receives the slot's whole resolved classes, and since it runs once per configuration, a `ref` it reads doesn't update it. For a slot a component passes to a child, like the `label` of ChatPromptSubmit, the function applies to the parent's classes for it and the child receives the result.

If you build components with `useComponentProps`, the `ui` it returns only holds the component's own `ui` prop: a Theme's `ui` reaches the classes through `useComponentOverrides` instead of being merged into the prop.

::note
This can't be applied by a find and replace: a Theme class you relied on being dropped by a component's `ui`, or by a nested Theme, now applies unless it conflicts, so look at the slots both set.
::

### Theme context

`@nuxt/ui/composables` no longer exports the context `<UTheme>` provides: `ThemeContext`, `defaultThemeContext`, `injectThemeContext` and `provideThemeContext` are gone. The context now also carries the `unstyled` flag of the nearest `<UTheme>` and the `ui` config, `app.config.ui` at the root, so a context provided by hand would leave the components below it without their config.

To give a subtree prop defaults, wrap it in `<UTheme>` instead:

```diff
-<script setup lang="ts">
-import { computed } from 'vue'
-import { provideThemeContext } from '@nuxt/ui/composables'
-
-provideThemeContext({ defaults: computed(() => ({ button: { size: 'sm' } })) })
-</script>
-
 <template>
-  <slot />
+  <UTheme :props="{ button: { size: 'sm' } }">
+    <slot />
+  </UTheme>
 </template>
```

::note
This can't be applied by a find and replace: the `defaults` you provided move to the `props` of a `<UTheme>` in the template of the same component.
::
