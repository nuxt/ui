Nuxt UI v5 is currently in alpha. Follow the progress in the [v5 tracking issue](https://github.com/nuxt/ui/issues/6918) and share feedback on the [v5 roadmap](https://github.com/nuxt/ui/discussions/6610).

This guide lists the breaking changes from v4 and is updated as the alpha progresses.

## Migrate your project

Prefer to let your AI assistant do it? Install the [Nuxt UI MCP server](/docs/getting-started/ai/mcp) in your editor, then copy this prompt into your assistant:

::prompt
---
description: Migrate this project to Nuxt UI v5
prompt: |
  Migrate this project from Nuxt UI v4 to v5.

  Use the Nuxt UI MCP server as the source of truth. Read the migration guide with the `get-migration-guide` tool and follow it. Don't rely on memory for names, options or versions.

  Before making any change:

  1. Check that the working tree is clean and create a branch for the migration.
  2. Analyze the project. Detect the package manager, whether it is a Nuxt or a Vue app, and where Nuxt UI is configured: `nuxt.config.ts` or `vite.config.ts`, `app.config.ts` or the `app.use(ui)` call of the entry file, and the main CSS file.
  3. Go through each section of "Changes from v4" and search the project for what it changes: props, slots, classes, CSS variables, options and imports, in templates, scripts, CSS, content and tests.
  4. Give me a plan with the sections that apply and the files they touch, and wait for my go.

  Then apply the migration:

  1. Update `@nuxt/ui` to `@nuxt/ui@next` with the project's package manager, and install the optional peer dependencies of the components the project uses.
  2. Apply the sections one at a time, in the order of the guide.
  3. For the changes the guide says can't be applied by a find and replace, read each match in context and fix it by hand. Ask me when the right change depends on what I want.
  4. Run the type check after each section, then the build and the tests at the end.

  Several changes fail silently, so a passing type check isn't enough: search the project once more for the old names. When done, list what you changed per section, the places that need a visual check, and the ones you weren't sure about.
---
::

## Changes from v4

The sections below go from setup to theming to components. Apply them in this order.

Nuxt UI v5 needs Tailwind CSS 4.2 or later, see [Canonical Tailwind classes](#canonical-tailwind-classes) for why:

```diff [package.json]
-"tailwindcss": "^4"
+"tailwindcss": "^4.2"
```

The `useEditorMenu` composable imports TipTap, so it is no longer exported from `@nuxt/ui/composables`. Import it from its own entry:

### Stylesheet paths

The stylesheets move to `dist/runtime/css/`. `@import "@nuxt/ui"` resolves as before, a path into the package doesn't:

```diff
-@import "@nuxt/ui/runtime/index.css";
+@import "@nuxt/ui";
```

`#build/ui.css` now holds only the sources Tailwind scans, not the styles, so import `@nuxt/ui` instead of it too.

### Vue plugin `ui` option

With Vue, the `ui` option of the Vite plugin is removed. The icons move to its `icons` option, which bundles them, and the rest of your theme moves to the Vue plugin in your entry file:

```diff [vite.config.ts]
 ui({
-  ui: {
-    icons: {
-      close: 'i-lucide-circle-x'
-    },
-    button: {
-      slots: {
-        base: 'font-bold'
-      }
-    }
-  }
+  icons: {
+    close: 'i-lucide-circle-x'
+  }
 })
```

```diff [src/main.ts]
-app.use(ui)
+app.use(ui, {
+  ui: {
+    button: {
+      slots: {
+        base: 'font-bold'
+      }
+    }
+  }
+})
```

The options of `vite.config.ts` reached your app serialized, so a function slot was dropped, and a change restarted the dev server. In `main.ts` a function slot works like in Nuxt's `app.config.ts`, and a change reloads the page.

::note
The keys move from `vite.config.ts` to `main.ts`, which a find and replace within one file can't do. TypeScript reports them in `vite.config.ts`. In a plain JavaScript config they are silently ignored, and components lose the classes, defaults and icons they set.
::

### `theme.colors` option

The `theme.colors` option is removed. Components accept a fixed set of colors, `primary`, `secondary`, `success`, `info`, `warning`, `error` and `neutral`, which you still map to any Tailwind palette, now in your CSS (see [`ui.colors` option](#uicolors-option)). Themes no longer need to know your aliases at build time. Trimming the list no longer saves any CSS either, since a color now costs one class.

```diff
 export default defineNuxtConfig({
   ui: {
-    theme: {
-      colors: ['primary', 'secondary', 'tertiary']
-    }
   }
 })
```

An extra alias like `tertiary` is declared in your CSS instead, and applied to a component through its `--ui-accent` variable, or through its `color` prop once you add it to that component's `color` variant in `app.config.ts`. [Extend colors](/docs/getting-started/theme/design-system#extend-colors) shows both:

```diff
-<UButton color="tertiary" />
+<UButton class="[--ui-accent:var(--ui-tertiary)]" />
```

Its value moves to your CSS with the recipe. Nuxt UI no longer bridges its shades either, so declare `--color-tertiary-600` and the others in `@theme` if you use classes like `text-tertiary-600`.

A Chart series only resolves the seven aliases, give a custom one its CSS color, like `color: 'var(--ui-tertiary)'`. A `neutral` series is shade `50` in dark mode instead of white.

::note
TypeScript reports the removed option in `nuxt.config.ts` or `vite.config.ts` and a `color` value outside the seven aliases. In plain JavaScript they are silently ignored, and a component given an unknown color takes the color of its closest colored ancestor, or none. Moving a custom alias from `color` to `class` can't be done by a find and replace when the component already has a `class`, binds `color` dynamically, or takes the color per item.
::

### `ui.colors` option

Colors move from `app.config.ts` to your CSS, where the `@nuxt/ui/colors` Tailwind plugin points each alias at a palette. Nuxt UI no longer generates a `<style>` from your app config at runtime, and no longer ships Tailwind's color table to the browser:

```diff [app.config.ts]
 export default defineAppConfig({
   ui: {
-    colors: {
-      primary: 'indigo',
-      neutral: 'zinc'
-    }
   }
 })
```

```diff [main.css]
 @import "tailwindcss";
 @import "@nuxt/ui";
+
+@plugin "@nuxt/ui/colors" {
+  primary: indigo;
+  neutral: zinc;
+}
```

With Vue, remove `colors` from the `ui` option of the Vue plugin the same way. A custom palette keeps working by name, like `primary: brand` with `--color-brand-50` to `--color-brand-950` in `@theme`.

The plugin writes each alias as `--ui-color-primary-50` to `--ui-color-primary-950`. To change colors at runtime, like `updateAppConfig` did, set those variables in a `<style>` instead, as shown in [Change colors at runtime](/docs/getting-started/theme/design-system#change-colors-at-runtime).

::note
The seven aliases of a static `colors` object move as is. An extra alias like `tertiary` becomes a `--ui-tertiary` variable instead, see [`theme.colors` option](#themecolors-option). Colors set at runtime with `updateAppConfig` or by writing to `appConfig.ui.colors` can't be moved by a find and replace, and reading `appConfig.ui.colors` now gives `undefined`. TypeScript only reports the removed key in `app.config.ts` when `colors` is the only key under `ui`. Next to other keys, and in the options of the Vue plugin or plain JavaScript, it is silently ignored and the aliases keep their default palettes, so remove it by hand.
::

### Default colors

The default palettes change. `primary` goes from `green` to `sky`, `secondary` from `blue` to `violet`, `success` from `green` to `emerald`, `warning` from `yellow` to `amber` and `neutral` from `slate` to `gray`. `info` and `error` keep `blue` and `red`. To keep the v4 palettes, list them in the plugin:

```diff [main.css]
 @import "tailwindcss";
 @import "@nuxt/ui";
+
+@plugin "@nuxt/ui/colors" {
+  primary: green;
+  secondary: blue;
+  success: green;
+  warning: yellow;
+  neutral: slate;
+}
```

An alias follows a palette you override in `@theme`, so shades of your own for `--color-green-*` or `--color-slate-*` no longer reach `primary`, `success` or `neutral` by default. List those aliases in the plugin too. The semantic tokens keep their shades.

An alias on a gray palette, like `primary: zinc`, now styles its `soft`, `outline`, `subtle`, `ghost` and `link` variants like `color="neutral"`. The `old-neutral` utilities are gone, declare the shades you need in `@theme`.

### `theme.transitions` option

The `theme.transitions` option is removed. Components always carry their transition classes, such as `transition-colors` on hover and active states, and movement transitions already stop when the user asks for reduced motion.

```diff
 export default defineNuxtConfig({
   ui: {
-    theme: {
-      transitions: false
-    }
   }
 })
```

To keep transitions off across your app, turn them off in your CSS instead:

```css [main.css]
@layer base {
  *, ::before, ::after {
    transition: none !important;
  }
}
```

::note
TypeScript reports the removed option in `nuxt.config.ts`. In a `vite.config.ts` or a plain JavaScript config it is silently ignored, and transitions come back.
::

### `theme.defaultVariants` option

The `theme.defaultVariants` option is removed. The default `color` and `size` are resolved at runtime now, so move them to `ui.defaultVariants` in your `app.config.ts`. They still only replace the `primary` and `md` defaults.

```diff [nuxt.config.ts]
 export default defineNuxtConfig({
   ui: {
-    theme: {
-      defaultVariants: {
-        color: 'neutral',
-        size: 'sm'
-      }
-    }
   }
 })
```

```diff [app.config.ts]
 export default defineAppConfig({
   ui: {
+    defaultVariants: {
+      color: 'neutral',
+      size: 'sm'
+    }
   }
 })
```

With Vue, the value moves from `theme` in your `vite.config.ts` to `ui` in the options of the Vue plugin, see [Vue plugin `ui` option](#vue-plugin-ui-option):

```diff [vite.config.ts]
 ui({
-  theme: {
-    defaultVariants: {
-      color: 'neutral',
-      size: 'sm'
-    }
-  }
 })
```

```diff [src/main.ts]
-app.use(ui)
+app.use(ui, {
+  ui: {
+    defaultVariants: {
+      color: 'neutral',
+      size: 'sm'
+    }
+  }
+})
```

To change them for part of your app only, use the `'*'` key of [`<UTheme :props>`](/docs/components/theme#default-variants): `<UTheme :props="{ '*': { size: 'sm' } }">`.

The themes in `#build/ui/*` no longer carry these defaults either: a theme you import from there keeps the library's `defaultVariants`.

::note
The value moves from `nuxt.config.ts` to `app.config.ts`, which a find and replace within one file can't do. TypeScript reports the removed option in `nuxt.config.ts`. In a `vite.config.ts` or a plain JavaScript config it is silently ignored, and components go back to `primary` and `md`.
::

### `theme.unstyled` option

The `theme.unstyled` option is removed. Components are unstyled at runtime now, per subtree with [`<UTheme unstyled>`](/docs/components/theme#unstyled) or app-wide with `ui.unstyled` in your `app.config.ts`:

```diff [nuxt.config.ts]
 export default defineNuxtConfig({
   ui: {
-    theme: {
-      unstyled: true
-    }
   }
 })
```

```diff [app.config.ts]
 export default defineAppConfig({
   ui: {
+    unstyled: true
   }
 })
```

With Vue, the value moves from `theme` in your `vite.config.ts` to `ui` in the options of the Vue plugin, like `defaultVariants`.

Components render the same markup as before: only the classes you supply through `class`, `ui` or `app.config.ui` remain, plus the `[--ui-accent:…]` class of the `color` prop, which styles nothing on its own. The theme classes are still in your CSS, so an unstyled app ships more CSS than in v4. A theme you import from `#build/ui/*` keeps its classes too.

::note
The value moves from `nuxt.config.ts` to `app.config.ts`, which a find and replace within one file can't do. TypeScript reports the removed option in `nuxt.config.ts`. In a `vite.config.ts` or a plain JavaScript config it is silently ignored, and components get their styles back.
::

### `theme.prefix` option

The `theme.prefix` option moves to `tailwindPrefix`. It was the last option under `theme`, which is removed:

```diff [nuxt.config.ts]
 export default defineNuxtConfig({
   ui: {
-    theme: {
-      prefix: 'tw'
-    }
+    tailwindPrefix: 'tw'
   }
 })
```

With Nuxt, you can also remove it when a stylesheet in your `css` option imports Tailwind CSS with the prefix, as Nuxt UI reads it from there. With Vue, it moves the same way in the plugin options of your `vite.config.ts`, and has to stay there: the Vite plugin doesn't read it from your CSS.

::note
TypeScript reports the old option in `nuxt.config.ts` and `vite.config.ts`. In a plain JavaScript config it is silently ignored: with Nuxt the prefix is still read from the stylesheet in your `css` option that imports Tailwind CSS, with Vue components render their classes without it.
::

Components now prefix their classes at runtime. They render the same classes, but the themes in `#build/ui` are unprefixed.

If you import a theme from `#build/ui/*` and read its classes yourself, they no longer carry the prefix. Resolve it with `tv` from `@nuxt/ui/utils/tv` and the overrides `useComponentOverrides` builds, as shown in [Variants engine](#variants-engine). These carry the prefix, and `tv` leaves the classes that already have it as they are.

### `inertia` option

The `inertia` option of the Vite plugin, deprecated since v4.3, is removed. Use `router: 'inertia'` instead:

```diff [vite.config.ts]
 ui({
-  inertia: true
+  router: 'inertia'
 })
```

TypeScript reports the removed option in `vite.config.ts`. In a plain JavaScript config it is silently ignored, and links go back to `vue-router`.

### `experimental.componentDetection` option

Component detection is on by default and leaves `experimental`, which is removed. Nuxt UI only generates the CSS of the components your app uses, so an app that didn't set the option ships less CSS, about 9 kB gzip less for an app that uses some 25 components:

```diff [nuxt.config.ts]
 export default defineNuxtConfig({
   ui: {
-    experimental: {
-      componentDetection: ['Modal']
-    }
+    componentDetection: ['Modal']
   }
 })
```

With Vue, it moves the same way in the plugin options of your `vite.config.ts`. Set `componentDetection: false` to keep the CSS of every component.

TypeScript reports `experimental` in `nuxt.config.ts` and `vite.config.ts`. In a plain JavaScript config it is silently ignored: detection stays on, but the components you listed are no longer added, so move the list.

::note
This can't be applied by a find and replace for apps that didn't set the option. Detection can miss a component resolved from a name built at runtime, like `<component :is="'U' + name" />`, or used only in remote content: list those in `componentDetection`. In development, such a component logs a warning in the browser console when it renders. Markdown in each layer's `content/` directory is scanned for `::u-button` and `:u-button`, and what prose components render is always included.
::

### `mdc` option

The `mdc` option, deprecated in favor of `prose`, is removed:

```diff [nuxt.config.ts]
 export default defineNuxtConfig({
   ui: {
-    mdc: true
+    prose: true
   }
 })
```

With Vue, it moves the same way in the plugin options of your `vite.config.ts`.

With Nuxt, `mdc: true` also added `@nuxtjs/mdc` to your modules. If you render Markdown with it, add it yourself:

```diff [nuxt.config.ts]
 export default defineNuxtConfig({
-  modules: ['@nuxt/ui']
+  modules: ['@nuxt/ui', '@nuxtjs/mdc']
 })
```

TypeScript reports the removed option in `nuxt.config.ts` and `vite.config.ts`. In a plain JavaScript config it is silently ignored, and the prose components are left out unless `@nuxtjs/mdc` or `@nuxt/content` is in your modules.

### `eslint` option

The [ESLint config](/docs/getting-started/integrations/eslint/nuxt) is on by default. It is added as soon as `@nuxt/eslint` and `eslint-plugin-better-tailwindcss` are both installed, without `eslint: true`, which you can remove:

```diff [nuxt.config.ts]
 export default defineNuxtConfig({
   ui: {
-    eslint: true
   }
 })
```

Set `eslint: false` to keep it off. Its rules also follow the v5 theme: raw colors suggest the [semantic tokens](#semantic-tokens) of v5, and the color aliases are read from the `@plugin "@nuxt/ui/colors"` block of your stylesheet instead of your `app.config.ts`.

::note
An app that has both packages installed but never set the option starts getting warnings. When its `eslint.config` registers `eslint-plugin-better-tailwindcss` itself, the config isn't added. When the plugin comes from a shared config you import, it can't be detected and ESLint fails with "Different instances of plugin": set `eslint: false`.
::

### Accent color

Component themes no longer repeat their classes for every color. The `color` prop sets a `--ui-accent` variable on the element, and the classes read it through new `accent` utilities such as `bg-accent`, `text-accent-contrast`, `bg-accent-soft` and `ring-accent-strong`. [Accent](/docs/getting-started/theme/css-variables#accent) lists the ones you can rely on.

Every color, `neutral` included, renders as before, with four exceptions and the changes listed in [Semantic tokens](#semantic-tokens). A colored linked Banner hovers at 75% like Button instead of 90%. Callout text uses the color itself instead of its 600 and 300 shades. A Timeline paints its pending indicators itself, so an item's `avatar.color` no longer tints them. The items of a CheckboxGroup with `variant="table"` take a Checkbox's own `color` instead of the group's.

```diff
-<button class="… text-inverted bg-primary hover:bg-primary/75 …">
+<button class="… [--ui-accent:var(--ui-primary)] text-accent-contrast bg-accent hover:bg-accent-hover …">
```

`:ui` overrides and `compoundVariants` keyed on `color` keep working, since `bg-accent` merges with `bg-primary` or `bg-red-500` like any other background color. What changes is the class names components render:

- Stylesheets, `querySelector` calls or tests that look for `.bg-primary` or `.text-error` on a component need to look for the `accent` classes and the `[--ui-accent:…]` class instead.
- A replacer function drops the `[--ui-accent:…]` class along with the classes it replaces, so the component loses its color. That covers a function on `variants.color` in `app.config.ui`, and a function in `:ui` or `class` on the slot that carries the color, usually the root: `<UInput :ui="{ root: () => 'w-full' }" />` now renders without one. Keep the scope class in what the function returns.
- An app that declares its own `--color-accent` in `@theme` overrides the one Nuxt UI declares, and every component follows it. Rename yours.
- The classes each variant takes for a color moved from the theme's `compoundVariants` into its `variants`. Your `app.config.ui` variants now come after them, so an override that used to lose silently applies, like `variants.variant.solid: { base: 'bg-red-500' }` on Button, which lost to `bg-primary`.

`neutral` is a color like the others. A new `--ui-neutral` variable, shade `900` of its palette in light mode and `50` in dark mode, goes through the same classes, and the neutral scope points the accent roles at the surface tokens such as `bg-soft`, `text-default` and `ring-strong`, so it keeps its current look.

Neutral rings and borders now use `--ui-neutral` where they used `--ui-border-inverted`, like the focus ring of Input. Light mode doesn't change. In dark mode, a solid neutral component and those rings use shade `50` instead of white. Neutral text, like the active link of Tabs or NavigationMenu, stays `text-strong`.

Setting `--ui-accent` through `class` also gives a component a color outside the `color` prop, without repeating its classes:

```vue
<UButton class="[--ui-accent:var(--color-indigo-500)]" variant="soft" />
<UInput highlight class="[--ui-accent:var(--color-indigo-500)]" />
```

::note
This can't be applied by a find and replace: selectors on color classes have to be read one by one, and the color name no longer appears in a component's classes, only in its `--ui-accent` class.
::

### Semantic tokens

The semantic tokens follow one set of words. `faint`, `muted`, `default` and `strong` are steps that mean the same on every property that has them, and a colored token is the neutral one with `accent-` in front: `bg-soft` is always neutral, `bg-accent-soft` follows `color`. The neutral solid is `--ui-neutral` itself, like a colored solid is the color, with `text-contrast` on it. Their CSS variables take the property they style as a prefix, like `--ui-bg-soft` or `--ui-border-strong`.

```diff
-<h2 class="text-highlighted">
+<h2 class="text-strong">
-<div class="bg-elevated hover:bg-accented">
+<div class="bg-soft hover:bg-strong">
-<div class="hover:bg-elevated/50">
+<div class="hover:bg-tint">
-<p class="text-dimmed">
+<p class="text-faint">
-<p class="text-toned">
+<p class="text-default">
-<div class="ring ring-accented">
+<div class="ring ring-strong">
-<div class="bg-inverted text-inverted">
+<div class="bg-neutral text-contrast">
```

| v4 class | v5 class | v4 variable | v5 variable |
| --- | --- | --- | --- |
| `text-highlighted` | `text-strong` | `--ui-text-highlighted` | `--ui-text-strong` |
| `text-default` | `text-default` | `--ui-text` | `--ui-text-default` |
| `text-toned` | `text-default` | `--ui-text-toned` | Removed, `--ui-text-default` |
| `text-dimmed` | `text-faint` | `--ui-text-dimmed` | `--ui-text-faint` |
| `text-inverted` | `text-contrast` | `--ui-text-inverted` | `--ui-text-contrast` |
| `bg-default` | `bg-default` | `--ui-bg` | `--ui-bg-default` |
| `bg-elevated/50` | `bg-tint` | | `--ui-bg-tint` (new) |
| `bg-muted` | `bg-tint` | `--ui-bg-muted` | Removed, `--ui-bg-tint` |
| `bg-elevated` | `bg-soft` | `--ui-bg-elevated` | `--ui-bg-soft` |
| `bg-accented` | `bg-strong` | `--ui-bg-accented` | `--ui-bg-strong` |
| `bg-inverted` | `bg-neutral` | `--ui-bg-inverted` | Removed, `--ui-neutral` |
| `border-default` | `border-default` | `--ui-border` | `--ui-border-default` |
| `border-muted` | `border-default` | `--ui-border-muted` | Removed, `--ui-border-default` |
| `border-accented` | `border-strong` | `--ui-border-accented` | `--ui-border-strong` |
| `border-inverted` | `border-neutral` | `--ui-border-inverted` | Removed, `--ui-neutral` |

The same renames apply with any variant or modifier, `hover:bg-accented/75` becoming `hover:bg-strong/75`. `ring-*`, `ring-offset-*`, `divide-*`, `outline-*`, `fill-*` and `stroke-*` follow the `border-*` rows, like `ring-inverted` becoming `ring-neutral`, and the gradient stops follow the `bg-*` rows, like `from-elevated` becoming `from-soft`. `outline-primary/25` used as a focus outline becomes `outline-focus`, and `outline-inverted/25` becomes `outline-neutral/25`. The Carousel dots, which used the second, and the Splitter handle, which had a solid `primary` outline, now focus with `outline-focus` like every component without a `color` prop. `bg-elevated` with another opacity keeps it, `bg-elevated/75` becomes `bg-soft/75`. `text-muted` and the `*-bg` utilities like `ring-bg` keep their names.

Four tokens are new. `--ui-bg-tint` is behind `bg-tint`, the fill of hovered and highlighted items, `--ui-bg-backdrop` behind `bg-backdrop`, the layer behind a Modal, a Slideover and a Drawer, `--ui-outline-focus` behind `outline-focus`, the focus outline of components without a `color` prop, and `--ui-neutral-bg-hover` behind `bg-neutral-hover`, the hover of the neutral solid. They're unset by default and mixed from other tokens, set one to replace the mix.

The tokens, with `--ui-radius`, `--ui-container` and `--ui-header-height`, move from `@layer theme` to `@layer base`. An override in `@layer theme` now loses, move it to `@layer base` or out of any layer.

A few components look different:

- The `outline` variants of Button, Badge, Kbd, Alert and ChatMessage and the selected day of an `outline` Calendar fill with `bg-default` for every color, like `neutral` did and like the `outline` Input. They look the same on the page. On a card, a filled area or an image, a colored one no longer shows what's behind it.
- Colored `link` variants are the color at 75% and turn to the full color on hover, instead of the full color turning to 75%, like neutral links go from `text-muted` to `text-default`. The colored text steps are the color at 50% for `faint` and 75% for `muted`, so the leading icons of colored DropdownMenu and ContextMenu items and a colored Avatar fallback are lighter.
- The `soft`, `subtle` and `outline` variants are the same classes on every component. Colored rings use one value for `outline` and `subtle`, the color at 50% like the `outline` ring of Button, Badge, Kbd and Calendar, instead of 25% for their `subtle` ring and on Alert and ChatMessage. For `neutral`, the ring of an `outline` Alert and of an `outline` or `subtle` ChatMessage is `border-strong` instead of `border-default`, and the fill of a `soft` or `subtle` Alert and ChatMessage is `bg-soft` instead of half of it. The text of a neutral `outline`, `soft` or `subtle` Alert is `text-default` instead of `text-highlighted`, like Button and Badge.
- A hovered prose Card looks like a `subtle` Button, `bg-accent-soft` with `border-accent-strong`: its border is the color at 50% instead of the full color. For `neutral` it is `bg-soft` with `border-strong`, instead of half of `bg-soft` with the `inverted` border.
- The active item of an EditorSuggestionMenu uses `bg-soft` instead of 75% of it.
- The `tint` role of the colors goes from 10% to 5% of the color, half of `soft` like `bg-tint` for neutral. Colored items highlighted in DropdownMenu and ContextMenu are lighter.
- Every former `bg-muted` surface, code blocks, inline code, neutral callouts, prompts, table heads, CodeCollapse and the Editor's code, uses `bg-tint`, a half step closer to the page in dark mode than `bg-muted`. Their border is `border-default`, shade `800` in dark mode instead of `700`, like the prose table cells.
- The FileUpload dropzone, hovered or with a file dragged over it, uses `bg-tint`, 50% of `--ui-bg-soft` instead of 25%.
- A Calendar goes through the same classes for every color, like Button: hovered and highlighted days use the `tint` step, 5% of the color or `bg-tint` for neutral, instead of 10% to 20%.
- The focused segment of a `soft` or `ghost` InputDate and InputTime uses `bg-strong`, highlighted lines of a code block use `bg-soft` and the delete button of an InputTags or InputMenu tag hovers on `bg-strong`, the same or one shade apart from their former mixes.
- A colored Separator draws its line with the `border-default` role, 25% of the color instead of the full color, like neutral draws `border-default`.
- A prose Callout and inline code go through the same classes for every color: colored ones fill at 5% of the color instead of 10%. Links in a neutral Callout take the neutral color instead of `primary`, and the external link icon of a colored Callout is the color at 50%.
- `text-toned` merges into `text-default`, one shade darker in light mode and lighter in dark mode, on BlogPost, ChangelogVersion, Empty, PageCard, PageCTA, PricingPlan, PricingTable, User and the prose Field.
- In dark mode, what used `bg-inverted` or `border-inverted`, like a solid Card, PageCTA or PricingPlan, uses shade `50` of the palette instead of white.

::note
The class and variable renames can be applied by a find and replace on whole names, counting `-` as part of the name, so that `--ui-text` doesn't catch `--ui-text-muted`, as long as `bg-elevated/50` is replaced before `bg-elevated`. An override of `--ui-text-toned`, `--ui-bg-inverted`, `--ui-border-inverted`, `--ui-bg-muted` or `--ui-border-muted` in your CSS has no token of its own left: move it to `--ui-text-default`, `--ui-neutral`, `--ui-bg-tint` or `--ui-border-default` if it should still apply. In dark mode, `border-muted` was shade `700` and `border-default` is `800`: write `border-default dark:border-strong` to keep the old border. An override of an old variable that the find and replace misses is silently ignored. Classes built at runtime, like `` `bg-${tone}` ``, have to be checked by hand.
::

::tip
The [ESLint config](/docs/getting-started/integrations/eslint/nuxt) finds the classes the find and replace missed. Turn on its `no-unknown-classes` rule while you migrate and every old token left in a `class`, a `:ui` object or your `app.config.ts`, like `text-highlighted` or `bg-elevated`, is reported as a class your stylesheet doesn't generate. Classes styled in your own CSS are reported too, list them in `ignore`.
::

### Heading font

Nuxt UI now reads `--font-heading` for the `h1` to `h6` elements and the titles of its components. If your `@theme` already declares `--font-heading` for a `font-heading` class of your own, those headings and titles now use it too. Rename it to keep them on the body font:

```diff [main.css]
 @theme {
-  --font-heading: 'Outfit', sans-serif;
+  --font-display: 'Outfit', sans-serif;
 }
```

Then replace `font-heading` with `font-display` in your own classes. If you set the heading font with an `h1, h2, h3, h4, h5, h6` rule of your own, `--font-heading` now does it, titles included, and the weights have their own [variables](/docs/getting-started/theme/css-variables#font).

### Gutter

The padding of the Card, Modal and Slideover parts, the Header menu, PageCard, BlogPost, the Prose card and the dashboard panels now reads the [`--ui-gutter`](/docs/getting-started/theme/css-variables#gutter) variable instead of `p-4 sm:p-6`. A padding you set on these slots through `class`, `ui` or `app.config.ui` now applies at every width, where the theme's `sm:p-6` used to win above `sm`. Write the breakpoint yourself to keep the old result, or set `--ui-gutter` to change all of them at once:

```diff [app.config.ts]
 export default defineAppConfig({
   ui: {
     card: {
       slots: {
-        body: 'p-3'
+        body: 'p-3 sm:p-6'
       }
     }
   }
 })
```

The Container reads it too, and loses its `lg:px-8` step: from `lg` up, the side padding of the page goes from `32px` to `24px`, so the content is `16px` wider. Add the step back on the Container to keep the old width:

```diff [app.config.ts]
 export default defineAppConfig({
   ui: {
+    container: {
+      slots: {
+        root: 'lg:px-8'
+      }
+    }
   }
 })
```

::note
This can't be applied by a find and replace: only an override without its own `sm:` padding changes, and whether it should keep the old `sm:p-6` or `lg:px-8` depends on the design.
::

### Container width

The `--ui-container` variable is now `--ui-container-width`, like `--ui-header-height`:

```diff [main.css]
 :root {
-  --ui-container: var(--container-8xl);
+  --ui-container-width: var(--container-8xl);
 }
```

An override of `--ui-container` is silently ignored. Replace it everywhere you set or read it, in your CSS and in classes like `max-w-(--ui-container)`.

### Canonical Tailwind classes

The component themes now write every class the way Tailwind CSS spells it today, the form its `suggestCanonicalClasses` lint reports. The styles are the same, the class names in the DOM and in the generated CSS change. Tailwind CSS 4.2 is the minimum version, since `inset-s-*` and `inset-e-*` replace the deprecated `start-*` and `end-*`:

Each row is one kind of rewrite:

| Before | After |
| --- | --- |
| `start-0`, `end-0` | `inset-s-0`, `inset-e-0` |
| `break-words` | `wrap-break-word` |
| `w-full h-full`, `-translate-x-1/2 -translate-y-1/2`, `mt-auto mb-auto` | `size-full`, `-translate-1/2`, `my-auto` |
| `z-[1]`, `aspect-[16/9]`, `-bottom-[10px]`, `!w-12` | `z-1`, `aspect-video`, `bottom-[-10px]`, `w-12!` |
| `data-[disabled]:opacity-75`, `[&:has([role=checkbox])]:pe-0`, `[&>[data-slot=avatar-icon]]:animate-spin` | `data-disabled:opacity-75`, `has-[[role=checkbox]]:pe-0`, `*:data-[slot=avatar-icon]:animate-spin` |

A class you pass through `class`, `ui` or `app.config.ui` still overrides the theme's when it's the same utility under either spelling: `start-2` replaces `inset-s-0`, `z-[5]` replaces `z-1` and `!p-2` replaces `p-0!`. Three cases need a look:

- A variant written the old way is no longer the same variant. `data-[disabled]:opacity-50` no longer removes the theme's `data-disabled:opacity-75`, both classes stay on the element. Write the variant as the theme does.
- `break-normal` no longer overrides the Accordion `label` or the Editor code blocks, which now use `wrap-break-word`. Use `wrap-normal`.
- A CSS selector that matches a class name, like `[class*="start-0"]`, has to follow the new name. The `data-slot` attributes are the stable way to target an element.

::note
This can't be applied by a find and replace: your own classes keep working under either spelling, so only the overrides that share a variant or a utility with one of the rewritten theme classes need a change.
::

The themes also move off the deprecated `bg-gradient-to-*` utilities, which Tailwind renamed to `bg-linear-*` in v4. Same CSS, so this only matters if your own stylesheet targets those class names on Marquee or PageAside.

### Theme shape

Every component now declares its elements under `slots`, and classes in `variants` and `compoundVariants` are always given per slot.

Components made of a single element, such as [Container](/docs/components/container), [Kbd](/docs/components/kbd), [Skeleton](/docs/components/skeleton) or the prose `p`, `li` and `code`, used to be themed with a top-level `base` key. They now have one slot like any other component, which some of them rename to `root` (see [`root` slot](#root-slot) below):

```diff
 export default defineAppConfig({
   ui: {
     container: {
-      base: 'max-w-5xl'
+      slots: {
+        root: 'max-w-5xl'
+      }
     },
     prose: {
       p: {
-        base: 'leading-7'
+        slots: {
+          base: 'leading-7'
+        }
       }
     }
   }
 })
```

This applies to BlogPosts, ChatShimmer, Container, DashboardGroup, DashboardResizeHandle, DashboardSidebarCollapse, DashboardSidebarToggle, FieldGroup, Form, Kbd, Link, Main, PageBody, PageColumns, PageGrid, PageList, PricingPlans and Skeleton, and to the prose `a`, `accordion-item`, `badge`, `blockquote`, `card-group`, `code`, `em`, `field-group`, `hr`, `icon`, `kbd`, `li`, `ol`, `p`, `steps`, `strong`, `tabs-item`, `tbody`, `td`, `th`, `thead`, `tr` and `ul`. [Link](/docs/components/link) gains a `ui` prop along the way.

A class written as a plain string in `variants` or `compoundVariants` used to apply to the `base` slot. It now has to name its slot:

```diff
 export default defineAppConfig({
   ui: {
     button: {
       variants: {
         size: {
-          md: 'text-base'
+          md: {
+            base: 'text-base'
+          }
         }
       },
       compoundVariants: [{
         color: 'neutral',
         variant: 'outline',
-        class: 'ring-default hover:bg-accented'
+        class: {
+          base: 'ring-default hover:bg-strong'
+        }
       }]
     }
   }
 })
```

The slot to name is the one `base` stood for: `root` on the components listed under [`root` slot](#root-slot), `base` on the others, Button included. TypeScript reports both changes in `app.config.ts`. In the options of the Vue plugin or a plain JavaScript config the classes are ignored: a bare class in `variants` or `compoundVariants` gets a warning in the console during development, a top-level `base` gets none.

::note
A find and replace can't apply these on its own: the top-level `base` only moves for the components listed above, since every other component already had it under `slots`, and a `class` string only has to be wrapped inside `compoundVariants`, not where `class` is a prop. Overrides built at runtime rather than written as literals have to be checked by hand. If you call `tv` yourself from `@nuxt/ui/utils/tv`, the same two rules apply to the themes you pass it, and it now always returns one function per slot. Classes go to those slot functions, `ui.base({ class })`, since the call that builds them only takes variants.
::

### Theme slot classes

The `ui` of a `<UTheme>` now merges with the `ui` of the components inside it, and with the `ui` of the Themes around it, instead of being replaced by them on the same slot. The nearest still wins a conflict, and the other classes still apply, so you no longer repeat the Theme's classes to keep them:

```diff
 <UTheme :ui="{ button: { base: 'rounded-full shadow-lg' } }">
-  <UButton :ui="{ base: 'rounded-none shadow-lg' }" />
+  <UButton :ui="{ base: 'rounded-none' }" />
 </UTheme>
```

A Theme's slot classes and `variants` apply at the same point as your app config's, after the whole theme, compound variants included, and the nearest Theme wins.

To drop a Theme's classes on one component, give the component's own `ui` a function, which replaces everything the slot resolved.

A function in a Theme's `ui` now works like one in `app.config.ui`: it replaces the theme's classes for that slot, and `app.config.ui` and other Themes still apply on top. It no longer receives the slot's whole resolved classes, and since it runs once per configuration, a `ref` it reads doesn't update it. For a slot a component passes to a child, like the `label` of ChatPromptSubmit, the function applies to the parent's classes for it and the child receives the result.

If you build components with `useComponentProps`, the `ui` it returns only holds the component's own `ui` prop: a Theme's `ui` reaches the classes through `useComponentOverrides` instead of being merged into the prop.

::note
This can't be applied by a find and replace: a Theme class you relied on being dropped by a component's `ui`, or by a nested Theme, now applies unless it conflicts, so look at the slots both set.
::

### Variants engine

Nuxt UI no longer depends on [Tailwind Variants](https://www.tailwind-variants.org/). Components are styled by an engine that ships with the library. `slots`, `variants`, `compoundVariants` and `defaultVariants` behave as before, and every theme in Nuxt UI resolves to the same classes.

Your `:ui` overrides keep working untouched. `app.config.ui` keeps its shape apart from the two changes described in [Theme shape](#theme-shape), but the order its classes apply in changes, see below. What follows only matters if you use `tailwind-variants` directly, or rely on one of the edge cases listed at the end.

If you import `tailwind-variants` in your own code, it is no longer installed for you:

::code-group{sync="pm"}

```bash [pnpm]
pnpm add tailwind-variants
```

```bash [yarn]
yarn add tailwind-variants
```

```bash [npm]
npm install tailwind-variants
```

```bash [bun]
bun add tailwind-variants
```

::

If you import its types, `@nuxt/ui` exports its own for the surface the engine supports: `ClassValue`, `ClassProp`, `TVTheme`, `TVOverrides`, `TVVariants`, `TVCompoundVariants`, `TVDefaultVariants`, `TVProps`, `TVReturnType`, `TVSlots` and `VariantProps`:

```diff
-import type { ClassValue, VariantProps } from 'tailwind-variants'
+import type { ClassValue, VariantProps } from '@nuxt/ui'
```

The config type is renamed, since `TVConfig` already means something else in Nuxt UI (the shape of `app.config.ui`):

```diff
-import type { TVConfig } from 'tailwind-variants'
+import type { TVMergeConfig } from '@nuxt/ui'
```

The generics take one type argument, the theme: `TVVariants<T>`, `TVCompoundVariants<T>`, `TVDefaultVariants<T>`, `TVProps<T>` and `TVReturnType<T>`, with `TVTheme` for what a theme may contain and `TVOverrides<T>` for what `app.config.ui` may add to one. Types with no equivalent, such as `TVCompoundSlots` or `TVLite`, describe features the engine doesn't have.

The engine's own `tv` takes the theme and the overrides as two arguments, and what it returns is only callable, it no longer carries the theme it was built from:

```diff
-const ui = tv({ extend: theme, ...appConfig.ui?.button })(props)
+const ui = tv(theme, appConfig.ui?.button)(props)
```

Called with plain overrides, `tv` merges with the default config and applies no prefix: it no longer reads `app.config.ui.tv` or `tailwindPrefix` itself. To resolve classes the way Nuxt UI's components do, with those two and `<UTheme unstyled>`, pass it the overrides `useComponentOverrides` builds:

```diff
+import { useComponentOverrides } from '@nuxt/ui/composables'
+
-const appConfig = useAppConfig()
-const ui = computed(() => tv(theme, appConfig.ui?.myComponent)(props))
+const overrides = useComponentOverrides(ui => ui.myComponent)
+const ui = computed(() => tv(theme, overrides.value)(props))
```

`useComponentOverrides` reads your component's entry from `app.config.ui`, then from the `ui` and `variants` of each `<UTheme>` around it.

::note
None of these changes can be applied by a find and replace: `TVConfig` is a valid Nuxt UI type too, so only imports coming from `tailwind-variants` should change, the type argument lists have to be read one by one, and a `tv` call has to be split where `extend` sits in its object.
::

Slot classes set in `app.config.ui` now win over the theme's `variants` and `compoundVariants`, the way the `ui` prop always has. They used to be merged beneath them, so a class like `text-inherit` on a slot silently lost to a theme variant setting `text-muted`, and the only way around it was to repeat the theme's variant combination in your own `compoundVariants`:

```diff
 export default defineAppConfig({
   ui: {
     avatar: {
       slots: {
         fallback: 'text-inherit'
-      },
-      compoundVariants: [{
-        color: 'neutral',
-        class: { fallback: 'text-inherit' }
-      }]
+      }
     }
   }
 })
```

The order is now the whole theme first, its slot classes, `variants` and `compoundVariants`, then yours in the same order, then the `ui` and `class` props. So anything you set wins over the theme, whatever form the theme rule takes.

That includes the padding of an icon-only Button. A padding you set on a size replaces the one `square` gives, so the button is no longer square. Set the [control tokens](#control-sizes) of the size instead, and `square` follows:

```diff
 export default defineAppConfig({
   ui: {
     button: {
       variants: {
         size: {
-          md: { base: 'px-4 py-2' }
+          md: { base: '[--ui-control-px:--spacing(4)] [--ui-control-py:--spacing(2)]' }
         }
       }
     }
   }
 })
```

A slot class that conflicts with one of the theme's variants or compounds now wins over it. A ring color on every checkbox, `checkbox.slots.base: 'ring ring-black/8'`, hides the red ring a checkbox shows in a form error through `highlight`. Scope it to the case instead:

```diff
 export default defineAppConfig({
   ui: {
     checkbox: {
       slots: {
-        base: 'ring ring-black/8'
+        base: 'ring'
-      }
+      },
+      variants: {
+        highlight: {
+          false: { base: 'ring-black/8' }
+        }
+      }
     }
   }
 })
```

Overriding one variant no longer changes the order the theme's own variants apply in, which used to let an unrelated theme variant win on another slot. Function slots still replace the default classes with the variants on top. They run once per configuration, so a `ref` they read doesn't update them, see [function slots](/docs/getting-started/theme/components#function-slots).

The `activeClass` and `inactiveClass` props of [Link](/docs/components/link) and [Button](/docs/components/button) follow the same rule. They were folded into the `active` variant, so a class like `hover:text-primary` lost to the theme's own `hover:text-default`. They are now merged last, after the `class` prop.

::note
This can't be applied by a find and replace. A slot class that was losing to the theme starts to apply, so look at the components you override in `app.config.ui` for classes that conflict with one of their variants, and drop the `compoundVariants` you only wrote to force a slot class through.
::

Classes are merged by `cn` instead of `tailwind-merge`. Every Nuxt UI theme renders the same classes as before. The one difference in your own classes is `bg-gradient-to-*`, the v3 name Tailwind renamed to `bg-linear-*`, which `cn` reads as a background image where `tailwind-merge` read it as a background. So it now survives a later `bg-<color>`, and it replaces a background image set before it instead of sitting next to it: `class="bg-gradient-to-r"` on a ChatShimmer or on a PageAside `topFooter` drops the gradient their theme sets, where it used to keep both. Write `bg-linear-to-r` and set the theme's slot through `:ui` if you meant to replace it.

`tailwind-merge` is no longer installed for you, so add it if you import it in your own code:

```bash
pnpm add tailwind-merge
```

The `app.config.ui.tv` keys were named after `tailwind-merge`. They are now named after what they do, and `twMergeConfig` is removed: its two options that have an equivalent, `prefix` and `cacheSize`, move to `app.config.ui.tv` itself. `prefix` is still set for you from the [`tailwindPrefix`](#themeprefix-option) module option:

```diff
 export default defineAppConfig({
   ui: {
     tv: {
-      twMerge: false,
-      twMergeConfig: { prefix: 'tw' }
+      merge: false,
+      prefix: 'tw'
     }
   }
 })
```

Extending the merger's class groups has no equivalent, and `TWMergeConfig` is gone with it. If you relied on custom `classGroups` or `conflictingClassGroups`, open an issue with what you were merging.

The engine leaves out three things `tailwind-variants` accepted, none of which any Nuxt UI theme uses:

- `compoundSlots`. A theme that declares it loses those classes silently, since nothing reads the key. Move each entry to a per-slot `class` object in `compoundVariants`, or to the slots themselves when it had no condition.
- The second `config` argument of `tv()`. `app.config.ui.tv` is the one place to configure merging.
- The `className` alias of `class`, a React convention with no meaning in Vue. A `compoundVariants` entry in `app.config.ui` that used it should say `class`.

One edge case resolves differently:

- A `(defaults) => classes` replacer on a slot with no classes now receives `''`, where it used to receive `undefined` and could emit the class `undefined`. Under `<UTheme unstyled>` this means the replacer runs where it used to be skipped.

### `mergeClasses` utility

`mergeClasses` is removed from `@nuxt/ui/utils`. Nothing in the library used it, and it only put two class values in one array, so write the array:

```diff
-import { mergeClasses } from '@nuxt/ui/utils'

-const classes = mergeClasses(appConfig.ui.myComponent?.base, props.class)
+const classes = [appConfig.ui.myComponent?.base, props.class]
```

### Theme context

`@nuxt/ui/composables` no longer exports the context `<UTheme>` provides: `ThemeContext`, `injectThemeContext` and `provideThemeContext` are internal now, and `defaultThemeContext` is gone. The context now also carries the `unstyled` flag of the nearest `<UTheme>` and the `ui` config, `app.config.ui` at the root, so a context provided by hand would leave the components below it without their config.

To give a subtree prop defaults, wrap it in `<UTheme>` instead:

```diff
-<script setup lang="ts">
-import { computed } from 'vue'
-import { provideThemeContext } from '@nuxt/ui/composables'
-
-provideThemeContext({ defaults: computed(() => ({ button: { size: 'sm' } })) })
-</script>
-
 <template>
-  <slot />
+  <UTheme :props="{ button: { size: 'sm' } }">
+    <slot />
+  </UTheme>
 </template>
```

::note
This can't be applied by a find and replace: the `defaults` you provided move to the `props` of a `<UTheme>` in the template of the same component.
::

### `root` slot

Slot names now follow one rule. `base` is the element a component stands for: a Button, a Badge, the `<input>` of an Input or the trigger of a Select, and the HTML element of a prose component, the `<p>`, the `<h1>`, the `<pre>`. Some of them wrap it in a `root`, others render it alone. On every other component, the outermost element is `root`.

The layout containers that called it `base` have it renamed, in `app.config.ui`, in the `ui` prop and in `<UTheme :ui>`:

```diff
-<UContainer :ui="{ base: 'max-w-5xl' }" />
+<UContainer :ui="{ root: 'max-w-5xl' }" />
```

```diff
 export default defineAppConfig({
   ui: {
     pageGrid: {
       slots: {
-        base: 'gap-4'
+        root: 'gap-4'
       }
     }
   }
 })
```

This applies to BlogPosts, Container, DashboardGroup, DashboardResizeHandle, FieldGroup, Form, Main, PageBody, PageColumns, PageGrid, PageList and PricingPlans. On [EditorToolbar](/docs/components/editor-toolbar), the toolbar moves from `base` to `root` and the bubble or floating menu around it from `root` to `menu`.

Everything else keeps its `base` slot: Button, Link, Badge, Kbd, Skeleton, ChatShimmer, every input and select apart from InputDate and InputTime, whose box is `root`, the prose components, and the buttons built on Button (ChatPromptSubmit, ContentSearchButton, DashboardSearchButton, DashboardSidebarCollapse, DashboardSidebarToggle). Toaster keeps it too, where it is each toast.

::note
A find and replace can't apply this blindly: `base` has to be renamed on the components listed here and kept on the others, so every match has to be read with the component it belongs to. TypeScript reports a leftover `base` in `app.config.ts` and on the `ui` prop in templates. In a `ui` object built at runtime, or in a plain JavaScript config, it is silently ignored.
::

### `data-slot` attributes

Every `data-slot` now carries the name of its component. They used to be shared, so `[data-slot="root"]` or `[data-slot="title"]` matched every component on the page. The outermost element of a component is named after it, and every other element is `<component>-<slot>`, with the slot written as in the theme:

```diff
-<div data-slot="root">
-  <div data-slot="header">
-    <div data-slot="title">
+<div data-slot="card">
+  <div data-slot="card-header">
+    <div data-slot="card-title">
```

```diff
-[data-slot="root"] { … }
+[data-slot="card"] { … }

-<UTabs :ui="{ trigger: 'in-[[data-slot=list]]:font-bold' }" />
+<UTabs :ui="{ trigger: 'in-[[data-slot=tabs-list]]:font-bold' }" />
```

The component name is the one in the docs URL, `page-hero`, `navigation-menu`, `content-toc`. The outermost element is the `root` slot, or `base` on the components that have no `root`, such as Button and Select, so `[data-slot="base"]` on a button becomes `[data-slot="button"]`. Overlays have no root element: their teleported content is `modal-content`, `popover-content`, `tooltip-content`.

A slot that renders another component is named after the component that owns the slot, not the one it renders. The icon of a Button is `button-leadingIcon`, the container of a PageHero is `page-hero-container`. The rendered component's own name only shows where you use it directly: a standalone `<UIcon>` has none and a standalone `<UContainer>` is `container`. What sits inside it keeps its own names, so the icon inside the avatar of an Empty is `avatar-icon`.

Components that emitted no `data-slot` now have one on their root, among them Container, Form, FieldGroup, Kbd, Link, Main, Skeleton, the Page layout components and the buttons built on Button. Prose components still emit none.

To find what to update:

```bash
rg -n "data-slot=[\"']?[A-Za-z]|data-\[slot=" --glob '!node_modules'
```

::note
This can't be applied by a find and replace, and no codemod covers it: the selectors live in stylesheets, in class strings, in `querySelector` calls and in end-to-end tests, and the same old value maps to a different new one depending on the component it belongs to, `leadingIcon` being `button-leadingIcon` in one place and `input-leadingIcon` in another. Inspect the element in the browser to read its new value. A selector that is left behind stops matching without any error.
::

### Child sizes

Themes no longer carry the size of the avatars, chips, badges and kbds a component renders. The `*Size` slots (`leadingAvatarSize`, `itemLeadingAvatarSize`, `itemLeadingChipSize`, `itemTrailingKbdsSize`, `avatarSize`, `linkLeadingAvatarSize`, `linkLeadingChipSize`, `linkTrailingBadgeSize`, `trailingBadgeSize` and `kbdsSize`) held size values, not classes, so they are removed. Each component now picks the same sizes in code: from its own `size` where it did before, and the fixed ones it always used otherwise, like the `2xl` avatar of Alert and Toast or the `sm` kbds of Tooltip. Set it on the child instead:

```diff
-<UButton :avatar="{ src: '/avatar.png' }" :ui="{ leadingAvatarSize: 'xs' }" />
+<UButton :avatar="{ src: '/avatar.png', size: 'xs' }" />
```

Items take it the same way, through `item.avatar.size`, `item.chip.size` or a kbd's `size`. A `*Size` value set in `app.config.ts` has no equivalent: `<UTheme :props="{ avatar: { size: 'xs' } }">` only sizes standalone avatars, since a component passes its own size to its child. Set `avatar.size` on each instance, or size the child with classes through its slot, like `leadingAvatar: 'size-4'`, in the `ui` prop or in `app.config.ts` for every instance. A size you add to a component yourself, like an `xxs` Button, gets the child sizes of `md`, since there's no slot left to set them for it.

In a slot template, `ui.leadingAvatarSize()` and the other `*Size` slot functions are gone. Set the size of your own avatar or chip directly: at the default size, `2xs` for an avatar, `3xs` in a Badge and `md` for a chip.

::note
This can't be applied by a find and replace: the size moves from `ui` to a prop of the child, which differs per component and per item.
::

### Control sizes

Button, Badge, Input, InputDate, InputMenu, InputNumber, InputTags, InputTime, Select, SelectMenu and Textarea no longer write the padding, gap and icon size of a `size` as classes. Each size sets four variables, `--ui-control-px`, `--ui-control-py`, `--ui-control-gap` and `--ui-control-icon-size`, and the classes read them. The links and labels of a NavigationMenu do the same with their fixed values. Checkbox and RadioGroup set three of them per size, without the gap: the padding of their `card` and `table` items and the size of their icon. Components render the same as before.

```diff
-<button class="… px-2.5 py-1.5 text-sm gap-1.5 …">
+<button class="… px-(--ui-control-px) py-(--ui-control-py) gap-(--ui-control-gap) [--ui-control-px:--spacing(2.5)] [--ui-control-py:--spacing(1.5)] [--ui-control-gap:--spacing(1.5)] [--ui-control-icon-size:--spacing(5)] text-sm …">
```

Your overrides keep working: `px-4` replaces `px-(--ui-control-px)`, and `size-4` on `leadingIcon` replaces the icon size. The theme compound variants for these sizes are gone, and the fields no longer reserve padding for an icon or a button, see [Fields](#fields). Slider, Progress, ProgressGroup and Separator do the same with `--ui-control-thickness`, the height of their track or the width of their line, and lose their `orientation` × `size` compound variants. Calendar sizes its cells with `--ui-control-size` and loses its `size` × `view` ones. Timeline writes the size of its indicator there and loses its `size` × `orientation` ones, Stepper its vertical ones, and FileUpload its `size` × `variant` ones. [Control](/docs/getting-started/theme/css-variables#control) lists the variables.

::note
Stylesheets, `querySelector` calls or tests that look for a padding or an icon size class on these components, like `.px-2\.5` or `.size-5`, need to read the variable instead. A `compoundVariants` entry of yours keyed on `leading`, `trailing` or `square` still applies.
::

The `square` prop of Button and Badge reads the vertical padding of the size, so it follows a size you restyle. NavigationMenu gains the same prop, which replaces a hardcoded padding:

```diff
-<UNavigationMenu :ui="{ link: 'p-1.5' }" />
+<UNavigationMenu square />
```

### Fields

The box of a field is now its outermost element. Input, Textarea, InputNumber, InputMenu and InputTags styled the native `<input>` or `<textarea>` as the box, with the `leading` and the `trailing` floating over it and a padding reserved for one icon. The native element now sits inside the box, next to the `leading` and the `trailing`, so anything you put in them takes its own room: a prefix, a `Kbd`, a button.

```diff
-<div data-slot="root">
-  <input data-slot="base" class="… ring bg-default rounded-md px-2.5 py-1.5 ps-9">
-  <span data-slot="leading" class="absolute …">…</span>
+<div data-slot="input" class="… ring bg-default rounded-md">
+  <input data-slot="input-base" class="… px-(--ui-control-px) py-(--ui-control-py) ps-(--ui-control-gap)">
+  <span data-slot="input-leading" class="order-first …">…</span>
 </div>
```

On the fields, the slots follow one rule: the `div` around everything is `root`, and the native element, an `<input>`, a `<textarea>` or a `<button>`, is `base`. So `root` is the box here and `base` is still the native element. A padding, a text size or a `placeholder:` class you set on `base` keeps working. What styles the box, a ring, a background, a radius, a border or a shadow, moves from `base` to the box. On an instance that is the `class` prop:

```diff
-<UInput :ui="{ base: 'rounded-full bg-muted' }" />
+<UInput class="rounded-full bg-tint" />
```

In your app config it is the `root` slot:

```diff
 export default defineAppConfig({
   ui: {
     input: {
       variants: {
         variant: {
-          outline: { base: 'ring-default focus-visible:ring-primary' }
+          outline: { root: 'ring-default has-[>:focus-visible]:ring-primary' }
         }
       }
     }
   }
 })
```

The box is not the element that takes the focus, so a state class changes its prefix when it moves: `focus:` becomes `has-[>:focus]:`, `focus-visible:` becomes `has-[>:focus-visible]:` and `disabled:` becomes `has-[>:disabled]:`. The focus outline is on the box as well, so `focus:outline-none` on `base` no longer removes it. On InputTags and InputMenu the input can sit inside the tags, so their box follows it with `has-[input:focus]:` and `has-[input:focus-visible]:`, and the box of InputTags is disabled with `data-disabled:`.

A `ps-*` or a `pe-*` you set to make room for the content of a `leading` or a `trailing` slot has to go, on Select, SelectMenu, InputDate and InputTime too: the room is no longer reserved, so the padding would add to it. An `absolute` you set on `leading` or `trailing` has to go as well, and a `pointer-events-none` there can go: a click on them already focuses the input.

```diff
-<UInput :ui="{ base: 'pl-14.5', leading: 'pointer-events-none' }">
+<UInput>
   <template #leading>
     <p class="text-sm text-muted">https://</p>
   </template>
 </UInput>
```

The radius is on the box as well. An input you made flush with a border, `variant="none"` with a `border-b` on its `class`, now needs `rounded-none` to keep the line straight.

::warning
This can't be done with a find and replace. Which classes move from `base` to `root` depends on what they style: the box or the native element.
::

The other fields follow the same layout:

- InputNumber holds its `increment` and `decrement` buttons in the flow of the box.
- InputTags follows the same names: `root` is the box, where it was `base`, and `base` is the native input, where it was `input`. The tags and the input wrap in a new `tags` slot. InputMenu has the same `tags` slot with `multiple`, and its `tagsInput` slot is now `base` as well.

  ```diff
  -<UInputTags :ui="{ base: 'rounded-full', input: 'placeholder:text-muted' }" />
  +<UInputTags :ui="{ root: 'rounded-full', base: 'placeholder:text-muted' }" />
  ```

- Select and SelectMenu are a single `<button>`, so `base` stays their box, with the `leading` and the `trailing` in its flow.
- InputDate and InputTime are a `div` around their segments, so their box is now `root`, where it was `base`.

  ```diff
  -<UInputDate :ui="{ base: 'rounded-full' }" />
  +<UInputDate :ui="{ root: 'rounded-full' }" />
  ```

The avatar of the `avatar` prop on Select, SelectMenu and InputMenu now uses the `leadingAvatar` slot, like Input. It was rendered with `itemLeadingAvatar`, the slot of the avatar of an item, so a class set there no longer reaches the trigger.

```diff
-<USelect :avatar="avatar" :ui="{ itemLeadingAvatar: 'rounded-sm' }" />
+<USelect :avatar="avatar" :ui="{ leadingAvatar: 'rounded-sm', itemLeadingAvatar: 'rounded-sm' }" />
```

Select loses its `empty` theme slot, which it never rendered. SelectMenu keeps its own.

What you put in the default slot of an Input or a Textarea is now inside the box, after the native element. A disabled field dims as a whole, with what it holds, and a click on the icon of a field focuses it. The resize handle of a Textarea sits at the end of the text, before a trailing icon.

### `fixed` prop

Input, Textarea, InputNumber, InputMenu, InputTags, InputDate, InputTime, Select, SelectMenu and PinInput no longer have a `fixed` prop, and their text is no longer larger below the `md` breakpoint. A field has the same text size on every screen, the one it had on desktop.

The larger text kept iOS Safari from zooming on a focused field at the `md` and `lg` sizes, which were 16px. To get it back, set `--ui-control-text-step` in your CSS: it is added to the text size of a field, at every size but `xl`, which is already 16px. The rule below gives the sizes of v4: 16px at `md` and `lg`, 14px at `xs` and `sm`.

```css [app/assets/css/main.css]
@media (width < 48rem) {
  :root {
    --ui-control-text-step: 0.125rem;
  }
}
```

The `fixed` prop kept the larger text on every breakpoint. Set the variable on the field instead:

```diff
-<UInput fixed />
+<UInput class="[--ui-control-text-step:0.125rem]" />
```

### `filter` prop

The prop that shows the filter input is now `filter` on every component that has one. It was `input` on CommandPalette, DashboardSearch and ContentSearch, and `searchInput` on SelectMenu. DropdownMenu and Listbox already called it `filter`. It still takes `false` to hide the input, or an object of [Input](/docs/components/input) props.

```diff
-<USelectMenu :search-input="false" />
+<USelectMenu :filter="false" />

-<UCommandPalette :input="false" />
+<UCommandPalette :filter="false" />
```

The props that configured the filter input on their own move into `filter`. On CommandPalette, DashboardSearch and ContentSearch, `placeholder`, `icon`, `trailing-icon` and `autofocus` are now keys of `filter`, with the same defaults, and `icon: false` still hides the icon. On Listbox, `autofocus` and `autofocus-delay` move the same way. `loading` and `loading-icon` stay on the component.

```diff
-<UCommandPalette placeholder="Search..." icon="i-lucide-box" :autofocus="false" />
+<UCommandPalette :filter="{ placeholder: 'Search...', icon: 'i-lucide-box', autofocus: false }" />

-<UListbox filter autofocus />
+<UListbox :filter="{ autofocus: true }" />
```

The locale key of the filter input placeholder is now `filterPlaceholder` on every component: it was `placeholder` on CommandPalette and `search` on SelectMenu, Listbox and DropdownMenu. Rename them in a locale you made with `defineLocale`:

```diff
 commandPalette: {
-  placeholder: 'Type a command or search…'
+  filterPlaceholder: 'Type a command or search…'
 },
 selectMenu: {
-  search: 'Search…'
+  filterPlaceholder: 'Search…'
 }
```

A locale left on the old keys shows the key itself, `selectMenu.filterPlaceholder`, as the placeholder. TypeScript reports it in a `defineLocale<Messages>`.

The theme slot of that input follows the prop on all six components: `input` is now `filter`, and its `data-slot` is `select-menu-filter`, `command-palette-filter`, and so on.

```diff
-<UCommandPalette :ui="{ input: '[&>input]:h-12' }" />
+<UCommandPalette :ui="{ filter: '[&>input]:h-12' }" />
```

```diff
 export default defineAppConfig({
   ui: {
     selectMenu: {
       slots: {
-        input: 'border-b-0'
+        filter: 'border-b-0'
       }
     }
   }
 })
```

::warning
A prop left behind fails silently: Vue passes an unknown prop on as an attribute, so the filter input shows again where you hid it, and a `placeholder` or an `icon` set on a CommandPalette, a DashboardSearch or a ContentSearch is ignored. `search-input` can be renamed with a find and replace. The rest can't: `placeholder`, `icon`, `trailing-icon` and `autofocus` have to be merged into the `filter` object, and they keep their meaning on other components. The `input` prop and slot only change on the six components above: AuthForm keeps its `input` slot, and `input` is also the app config key of the Input component. Props passed through `v-bind` or `<UTheme :props>` have to be found by hand. TypeScript reports a leftover `input` slot in `app.config.ts` and on the `ui` prop, not in a `ui` object built at runtime.
::

### Stacked toasts

Toasts are now stacked by default: the `expand` prop of the Toaster defaults to `false`, and hovering or focusing the stack expands it. Set it back to `true` on the App to keep every toast visible:

```diff [app.vue]
-<UApp>
+<UApp :toaster="{ expand: true }">
   <NuxtPage />
 </UApp>
```

### Tabs `pill` variant

The `pill` variant of Tabs no longer fills the active tab with the color. The indicator is now a `bg-default` tab with a shadow on the `bg-soft` track, and the `color` prop sets the text of the active tab, like the `link` variant. With `color="neutral"`, the active tab is `text-strong`.

```diff
-<span data-slot="tabs-indicator" class="… bg-accent rounded-md shadow-xs …">
+<span data-slot="tabs-indicator" class="… bg-default rounded-md shadow-xs …">
-<button data-slot="tabs-trigger" class="… grow data-[state=active]:text-accent-contrast …">
+<button data-slot="tabs-trigger" class="… grow data-[state=active]:text-accent …">
```

To get the filled tab back, set the indicator and the active text in your `app.config.ts`:

```ts [app.config.ts]
export default defineAppConfig({
  ui: {
    tabs: {
      variants: {
        variant: {
          pill: {
            indicator: 'bg-accent',
            trigger: 'data-[state=active]:text-accent-contrast'
          }
        }
      }
    }
  }
})
```

### TanStack Table v9

The Table component moves to TanStack Table v9. Upgrade `@tanstack/vue-table` to `^9`, and read the [TanStack Table migration guide](https://tanstack.com/table/v9/docs/framework/vue/guide/migrating) for the changes in your column definitions, like `sortingFn` renamed to `sortFn`.

The table registers the features it renders: sorting, column and global filtering, expanding, row selection, column visibility, column pinning, sizing and resizing, and row pinning. Pagination, grouping, faceting and column ordering are registered with the new `features` prop, which replaces the row model getters you passed in the options props. Declare it in your script, it is read once:

```diff
 <script setup lang="ts">
-import { getPaginationRowModel } from '@tanstack/vue-table'
+import { createPaginatedRowModel, rowPaginationFeature } from '@tanstack/vue-table'
+
+const features = { rowPaginationFeature, paginatedRowModel: createPaginatedRowModel() }
 </script>

 <template>
-  <UTable :pagination-options="{ getPaginationRowModel: getPaginationRowModel() }" />
+  <UTable :features="features" />
 </template>
```

Grouping needs `columnGroupingFeature`, `rowAggregationFeature`, `createGroupedRowModel()` and the aggregation functions your columns name. Faceting needs `columnFacetingFeature` and the faceted row models, which replaces the `faceted-options` prop:

```diff
-<UTable :grouping-options="{ getGroupedRowModel: getGroupedRowModel() }" />
+<UTable :features="{ columnGroupingFeature, rowAggregationFeature, groupedRowModel: createGroupedRowModel(), aggregationFns: { sum: aggregationFn_sum } }" />

-<UTable :faceted-options="{ getFacetedRowModel: getFacetedRowModel(), getFacetedUniqueValues: getFacetedUniqueValues() }" />
+<UTable :features="{ columnFacetingFeature, facetedRowModel: createFacetedRowModel(), facetedUniqueValues: createFacetedUniqueValues() }" />
```

The `min`, `max` and `extent` aggregation functions only compare numbers and dates. A column of date strings returns `undefined`, return a `Date` from its accessor instead.

Aggregated cells of grouped rows now render the column's `aggregatedCell`, which TanStack Table fills with the formatted value by default, instead of its `cell`. Move what a `cell` rendered for grouped rows to `aggregatedCell`:

```diff
 {
   accessorKey: 'amount',
-  cell: ({ row }) => row.getIsGrouped() ? `Total ${row.getValue('amount')}` : row.getValue('amount'),
+  cell: ({ getValue }) => getValue(),
+  aggregatedCell: ({ getValue }) => `Total ${getValue()}`,
   aggregationFn: 'sum'
 }
```

The `colspan` and `rowspan` keys of a column `meta` are removed. Register `cellSpanningFeature` and use TanStack Table's `spanRows` and `spanColumns` column options instead: the cells they cover are no longer rendered, so the `hidden` class workaround goes away:

```diff
 {
   accessorKey: 'category',
-  meta: {
-    rowspan: { td: getCategoryRowSpan },
-    class: { td: cell => isCoveredCategory(cell) ? 'hidden' : '' }
-  }
+  spanRows: true
 }
```

A column under a group header now spans the rows of the group placeholders above it, as one `th` with a `rowspan`. Its `#<column>-header` slot renders in that cell, and the empty placeholder cells are gone. The footer keeps one cell per row.

The eleven feature options props merge into one `options` prop: `global-filter-options`, `column-filters-options`, `column-pinning-options`, `column-sizing-options`, `visibility-options`, `sorting-options`, `grouping-options`, `expanded-options`, `row-selection-options`, `row-pinning-options` and `pagination-options`. It takes any option of the registered features:

```diff
-<UTable :sorting-options="{ enableMultiSort: true }" :row-selection-options="{ enableRowSelection: row => row.original.active }" />
+<UTable :options="{ enableMultiSort: true, enableRowSelection: row => row.original.active }" />
```

The `on-state-change` prop is removed, TanStack Table v9 no longer has it. Bind the state you need with `v-model` instead. `v-model:column-sizing-info` is renamed `v-model:column-resizing`:

```diff
-<UTable v-model:column-sizing-info="columnSizingInfo" />
+<UTable v-model:column-resizing="columnResizing" />
```

Column pinning uses `start` and `end` instead of `left` and `right`, and pinned columns stick to the start or end side in the text direction. This changes the `column-pinning` state, `column.pin()` and the `data-pinned` attribute of the cells:

```diff
-const columnPinning = ref({ left: ['id'], right: ['actions'] })
+const columnPinning = ref({ start: ['id'], end: ['actions'] })

-column.pin('left')
+column.pin('start')
```

```diff
-<UTable :ui="{ td: 'data-[pinned=left]:shadow-md' }" />
+<UTable :ui="{ td: 'data-[pinned=start]:shadow-md' }" />
```

`tableApi` follows TanStack Table v9. `getState()` is gone: read a slice from its atom, or the whole state from the store:

```diff
-table.value?.tableApi?.getState().pagination
+table.value?.tableApi?.atoms.pagination.get()

-table.value?.tableApi?.getState()
+table.value?.tableApi?.store.state
```

The `Row`, `Column`, `Cell`, `Header` and `TableMeta` types from `@tanstack/vue-table` take the table features as their first argument. Pass `TableFeatures` from `@nuxt/ui`, or use `TableRow`. `TableColumn<T>` and `TableRow<T>` don't change:

```diff
-import type { Column, Row } from '@tanstack/vue-table'
+import type { TableFeatures, TableRow } from '@nuxt/ui'
+import type { Column } from '@tanstack/vue-table'

-function getHeader(column: Column<Payment>) {}
+function getHeader(column: Column<TableFeatures, Payment>) {}

-function getRowItems(row: Row<Payment>) {}
+function getRowItems(row: TableRow<Payment>) {}
```

`TableFeatures` includes every TanStack Table feature, so the API of a feature you didn't register type-checks on `tableApi` and fails at runtime.

Keep a row you store in a `shallowRef`. A `ref` makes the row and its table deeply reactive, and its type no longer matches `TableRow`:

```diff
-const selectedRow = ref<TableRow<Payment> | null>(null)
+const selectedRow = shallowRef<TableRow<Payment> | null>(null)
```

Row selection changes in four ways:

- `getIsSomeRowsSelected()` and `getIsSomePageRowsSelected()` are true as soon as one row is selected, the full selection included. A select all checkbox has to test `getIsAll…` first:

  ```diff
  -modelValue: table.getIsSomePageRowsSelected() ? 'indeterminate' : table.getIsAllPageRowsSelected()
  +modelValue: table.getIsAllPageRowsSelected() ? true : table.getIsSomePageRowsSelected() ? 'indeterminate' : false
  ```

- The `row-selection` state only holds selected rows, its values are always `true`. `{ 1: false }` no longer type-checks, leave the row out instead.
- Shift-click selects a range of rows by default through `row.getToggleSelectedHandler()`. Turn it off with `:options="{ enableRowRangeSelection: false }"`.
- With an `enableRowSelection` function, the rows it returns `false` for no longer get `data-selectable="true"`, so they lose the hover style of clickable rows.

::warning
Only the `column-sizing-info` rename can be done with a find and replace. Grouped `cell` renderers have to move to `aggregatedCell` and `meta.rowspan` / `meta.colspan` to `spanRows` / `spanColumns` by hand. The options props have to be merged into one `options` object, and their row model getters move to `features` with new names. `left` and `right` are common words, so the pinning state, `column.pin()` calls and `data-pinned` selectors have to be found by hand, as do `getState()` calls, the select all checkbox order and `false` values in a row selection state. A removed prop left behind fails silently, Vue passes it on as an attribute. TypeScript reports the old pinning keys, `false` selection values and the missing type arguments, not a `data-pinned` selector in a class string or the meaning change of `getIsSome…RowsSelected()`.
::
